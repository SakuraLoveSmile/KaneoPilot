# macOS 会话全文探针停顿调查施工计划

## 概要

- 问题：手动探针 `macos/tests/session_fulltext_main.swift` 在同一套 macOS 代码上得到 367.06、244.25、349.23 ms。指标是全程最大主线程延迟，单次停顿即决定 PASS 或 FAIL。
- 目标：找出造成 240–370 ms 停顿的具体操作，并判定它属于夹具、产品还是运行器环境。
- 不做：不放宽 250 ms；不改用 p95 等替代指标；不改产品 Swift 源码；不在本地编译；不改门禁与 publish。
- 状态：已结束（2026-10-28），归因为运行器环境，系统层候选（H4），见文末「归因结束」。阶段一与阶段一b已执行，两者都未归因。阶段一c（主线程状态轮询，不采样）已批准并执行：诊断提交 `2bd336f`，整轮运行 `40632514615`（attempt 1–3）。结果：停顿位于冷启动下首次 1 MB 安装的 install 开始至 locate 开始之间，主线程等待、CPU 占比约 0.1；未归因到具体操作。阶段二 C（尺寸对照）已执行：诊断提交 `e1bf4e1`，整轮运行 `40643910829`（attempt 1–6）。结果：冷启动停顿不随尺寸增长（65 537 字节中位数 644 ms，262 144 字节 417 ms，1 MB 参照 387 ms），判为争用或环境，转 D。随后的最小文本对照（诊断提交 `b5c583b`，整轮运行 `40648669163`，attempt 1–6 全部成功）修正了这一判读：停顿是作业内首次使用后台准备路径时的主线程等待，按预先约定判为产品路径（路线 B），归因未完成，见「阶段二 C 对照」节。随后的 T0 边界对照（产品计划「T0 结果」，整轮运行 `40653937723`）推翻了路线 B：同步路径的 64 KiB 冷启动也停顿，本计划的路线 B 结论已被取代。T0' 裸 AppKit 对照（产品计划「T0' 结果」，整轮运行 `40658656345`）判为系统层候选（H4）：裸冷启动 3/3 停顿，产品有效冷启动 2/3。文本形状对照（诊断提交 `89e250a`，整轮运行 `40673713768`，计划见 `macOS会话全文探针文本形状对照施工计划_20261028.plan.md`）：自然英文文本的裸冷启动同样停顿（3/3），文本形状不是触发因素；采样机制未排除。

### 慢采样的形态（推断，待时间戳核实）

- 两次失败的慢采样列表都严格递减。这与一次连续停顿期间排队的采样在停顿结束后依次执行的形态一致。若成立，则每次运行的最大值约等于一次停顿的长度。
- 相邻差值为 6–48 ms，而计时器周期是 10 ms。这说明计时器在停顿期间也可能延迟。日志没有时间戳，无法核实。
- 通过的一次中，p95 为 25.99 ms：大多数样本正常，停顿是少数。

### 已埋点的主线程操作都没有超过 200 ms

第 3 次失败的事件快照（`events`）中，主线程上的埋点操作最大值如下：

| 事件 | 计时范围 | 最大值 |
|---|---|---|
| `fulltext_attach` | `install()` 函数体（`SessionMessageDetailView.swift:495–517`） | 24.46 ms |
| `fulltext_first_draw` | 视图创建到首次 `draw` 结束（`:333–346`，含创建后的其他工作） | 88.71 ms |
| `fulltext_locate` | `scrollRangeToVisible`（`:536`） | 0.66 ms |
| `fulltext_stop` | `stop()`（`:574–587`） | 1.14 ms |
| `fulltext_panel_open` / `_close` | 面板展示与关闭 | 55.23 ms / 4.05 ms |

`fulltext_prepare` 最长 1163.53 ms，但 `main_thread` 为 false，在后台执行。

因此，≥200 ms 的停顿不在这些计时区间之内。这是推断，成立的前提是埋点之外确实有主线程工作；下文的候选正好位于埋点之外。

### 「textkit」标签不代表 TextKit

`probeStage` 只在 `session_fulltext_main.swift:229` 从 `textkit` 变为 `panel`。因此标签 `textkit` 覆盖第 92–228 行的全部步骤：初始大文本、缩放、陈旧代次、Unicode 大文本、Markdown、模式切换、交互与剪贴板。这些步骤里有大量夹具自身的主线程工作（见候选 1–5）。所以「TextKit 对 1 MB 文本的开销」不是首要假设。

## 阶段一：归因（只改夹具，不改产品源码）

改动只在 `macos/tests/session_fulltext_main.swift` 中进行；需要时才改 `run-session-fulltext-fixtures.sh`。

1. 时间戳：`SessionReaderPerformance` 桩的 `record` 与每个探针样本记录 `t_ms`（相对夹具启动的单调时钟毫秒）。
2. 步骤标签：把 `probeStage` 拆成步骤名：载入、缩放、陈旧代次、Unicode、Markdown、模式切换、交互、剪贴板、面板。样本的标签在**触发时**读取，而不是执行时。这样，停顿的起点能对应到开始阻塞的那一步。
3. 直接计时：候选 1–5 的每个夹具调用包进 `timed(label)`，记录同步耗时。
4. 看门狗：一个后台线程，休眠 5 ms，记录唤醒超时（≥50 ms 的时间点与幅度）。它不访问主线程。
5. 环境：夹具启动时输出 `activeProcessorCount`、`getloadavg` 与 `systemUptime`。
6. 报告：PASS 与 FAIL 都输出同一份 JSON。
   - `episodes`：每段 ≥200 ms 的停顿，含起点 `t_ms`、长度、起点步骤标签（取同段内最早触发的样本）。
   - `ops`：每个标签的次数、最大值、总耗时。
   - `watchdog`：超时列表。
   - `environment`。
   - 保留 `probe_max_ms` 与 `result` 字段，便于与历史结果对齐。
   - 耗时断言的阈值与「最大值」口径不变。诊断模式下只记录，不因耗时退出，以便同一作业顺序跑完各模式。

对照模式（同一诊断提交，用环境变量 `KANPILOT_PROBE_MODE` 切换，仅诊断用）：

- `full`：当前全部步骤。
- `attach`：载入 1 MB 文本，等待首次附着与绘制后结束，不做交互。
- `idle`：无文本，只运行计时器与看门狗，时长与 `full` 相当。

运行次数（开始前固定）：

- 诊断提交推送到诊断分支，提交信息加 `[skip ci]`，避免推送即整轮运行。首次使用时核对：推送被跳过，`workflow_dispatch` 仍运行。
- `gh workflow run packages.yml --ref <诊断分支> -f probe_session_fulltext=true` 一次（整轮）。
- 同一提交上 `gh run rerun <run> --job <探针作业 ID>` 两次（各约 41 秒）。
- 每个作业内，`full`、`attach`、`idle` 各跑 3 次。

归因成立的判定（阶段一结束时）：

- 3 个样本中至少 2 个出现 ≥200 ms 的停顿，且起点标签一致；
- 该标签内某个直接计时操作的单次耗时 ≥ 停顿长度的 80%；
- 看门狗结论与该停顿一致（不是进程级）。

满足则进入阶段二 A。起点标签一致但没有直接计时操作能解释，进入阶段一b。看门狗同时超时，进入阶段二 D。标签不一致，记为「未归因」，保留全部数据，并与你讨论是否增加样本。

## 阶段一b：冷启动采样（阶段一未归因，已进入）

依据：三个作业的停顿都出现在各自的首次运行（冷启动）；热启动的 24 次运行没有 ≥200 ms 停顿。阶段一的 attach 与 idle 从未排在首位，因此模式与冷启动无法区分。

- 只改 `macos/tests/run-session-fulltext-fixtures.sh`，夹具源码不变。
- 首个模式按 `GITHUB_RUN_ATTEMPT` 轮换：第 1 次 full，第 2 次 attach，第 3 次 idle。每个作业的第一次运行即冷启动，并被采样。
- 采样：在首次启动前后台执行 `sample <夹具进程名> -wait`，启动即附加，不依赖夹具内的时序。`-wait` 在托管镜像上是否可用，以首次云端运行为准；不可用时改用 `xctrace`（Time Profiler，云端执行）。
- 其余运行顺序不变，都是热启动，不采样。每个作业记录 `uptime` 与负载。
- 判定：
  - 冷启动 idle 也出现 ≥200 ms 停顿 → 与读取路径无关，是冷启动效应。
  - 只在 full、attach 冷启动出现 → 与读取路径有关。
  - 三次冷启动都没有 ≥200 ms 停顿 → 现象不稳定，需要更多冷启动样本，再决定是否进入阶段二。
  - 栈帧能指向 `KaneoPilot` 的具体符号或具体的系统框架调用，并能对应到载入窗口 → 退出标准达成。
- 采样会暂停目标进程，可能改变时序。采样运行单独统计，不与热启动混算。
- 运行次数：派发一次，重跑两次（三个冷启动）。本设计没有编译后等待的对照；若采样指向系统活动，再加等待对照。
- 结论的含义：若只是每个二进制的首次执行成本，影响限于 CI；若是 TextKit 或字体的首次使用成本，用户首次打开大消息时同样会遇到。

## 阶段一c：主线程状态轮询（阶段一b 未归因，已批准）

依据：阶段一b 的采样扰动时序（三个被采样运行的看门狗超时为 77.9–489.7 ms），且 `sample` 挂起目标，无法给出停顿内的时间分布。本阶段改为不挂起目标的计数。

- 只改 `macos/tests/run-session-fulltext-fixtures.sh` 与 `macos/tests/session_fulltext_main.swift`；产品源码不改。
- 运行脚本：去掉 `sample` 与首个运行的采样分支，保留按 `GITHUB_RUN_ATTEMPT` 轮换首个模式（attempt 1 为 full，2 为 attach，3 为 idle）。每次运行的输出另存为 `macos-reports/attempt-<n>-<模式>-<序号>.txt`；工作流仍把合并输出写入 `run-session-fulltext-fixtures.log`。
- 夹具：`run()` 位于主 actor，即主线程。它调用 `mach_thread_self()` 取得主线程端口。随后看门狗线程每约 5 ms 做两次调用，两者都不挂起线程：
  - `thread_info(主线程端口, THREAD_BASIC_INFO)`：`user_time`、`system_time`、`run_state`；
  - `task_info(mach_task_self_, TASK_EVENTS_INFO)`：进程级的 `pageins`、`csw`、`messages_sent + messages_received`。
- 报告新增 `main_thread_fields` 与 `main_thread_ticks`，每行为 `[t_ms, user_us, system_us, run_state, pageins, csw, messages]`。`t_ms` 与探针样本、`fulltext_*` 事件使用同一时钟（`Diagnostics.now()`）。
- 延迟仍只报告，不做门禁；`result`、`probe_max_ms`、`probe_p95_ms` 口径不变。
- 工件名为 `macos-session-fulltext-probe-<run_number>`。三次 attempt 的同名工件均上传成功（各自独立的工件 ID，见「实测记录」）。作业日志中的 `KANPILOT_PROBE_REPORT` 行是主要数据源。

判读规则（在读取本阶段数据之前确定）：

1. `run_state == 1` 表示运行中或可运行，不能区分「占用 CPU」与「等待 CPU」。停顿窗口内，用主线程 `user_us + system_us` 的增量除以窗口墙钟时长判断：接近 1 为占用 CPU，接近 0 为未占用。`run_state` 只用于区分 3（等待）、4（不可中断）与 1。
2. 看门狗被饿死时会缺少行，但 CPU 计数是累计值，停顿两端的两行仍能判断窗口内是否有 CPU 增量。缺口加上看门狗超时，说明整个进程被饿死。
3. `csw` 与 `messages` 包含探针自身的活动（`thread_info`、`task_info` 的 Mach 调用，以及 `usleep` 造成的上下文切换）。先从空载运行求出每个时间片的基线增量，再从窗口增量中扣除，然后才解读。`pageins` 不受此影响。
4. 先证明端口确为主线程：主线程 `user_us` 应随一次已知的长主线程操作增长（例如 `long_ops` 中的 `exactText@114`）。若不增长，端口错误，所有 tick 数据都不可解读，停止分析并报告。
5. 停顿窗口取 `episodes` 中最大的一段，窗口为 `[start_ms, start_ms + duration_ms]`，与阶段一b 相同。载入停顿还要核对 `fulltext_attach` 起点与 `fulltext_locate` 起点是否落在窗口内。

重跑前的完整性检查（attempt 1 通过后才重跑）：

- 每个 `KANPILOT_PROBE_REPORT` 行都能解析为完整 JSON；
- `len(main_thread_ticks)` 约等于该运行时长除以约 5.2 ms；
- 若能下载工件，其中应有 9 个运行的 `.txt` 文件加合并日志。

判定（阶段一c 结束时）：

- 窗口内 CPU 增量接近墙钟：主线程在计算，归入主线程同步工作（候选 6–9，或候选 12 的主线程部分）。
- CPU 增量接近零且 `run_state` 为 3：主线程在等待。扣除基线后 `csw` 或 `messages` 仍明显增加，指向 IPC 或系统服务（候选 11，或候选 12 的同步等待）；否则指向其他等待。
- CPU 增量接近零且 `run_state` 为 1：主线程可运行却未获得 CPU，指向 CPU 争用（候选 10、12，或环境）。
- `run_state` 为 4：不可中断，指向换入或 I/O（候选 11）。

判定按探针作业（3 个）分别报告，不合并计算。

## 阶段二 C：尺寸对照（已批准，已执行）

依据：阶段一c 未归因。冷启动的首个 1 MB 安装停顿为 378–477 ms，主线程等待而非计算。C 分支要检验这段停顿是否随文本尺寸增长。

- 尺寸口径：`utf8.count`，即总字节数，含 `TAILNEEDLE`。产品 `macos/KaneoPilot/Views/SessionMessageDetailView.swift:413` 以 `text.utf8.count <= 64 * 1024` 选择同步路径，该路径不记录 `fulltext_prepare` 与 `fulltext_attach`。因此 65 537 字节是最小的后台安装尺寸。
- 对照：65 537 与 262 144 字节（256 KiB），各 3 次。1 MB 参照取 1c 的冷启动结果（n=3），本阶段不重跑。
- 改动只在 `macos/tests/`：夹具新增诊断参数 `KANPILOT_PROBE_BYTES`（缺省为 1 MB，与 1c 相同）。只有 attach 模式允许改尺寸，其他模式遇到非缺省尺寸即 FAIL；运行脚本只跑 attach，`PROBE_RUN` 行追加 `bytes=`。产品源码不改。

判定（在读取本阶段数据前确定；按作业分别报告，不合并热态运行）：

## 阶段二 C 对照：最小文本（已执行）

依据：阶段二 C 显示，停顿在 65 537 字节到 1 MB 之间不随尺寸变化（冷启动中位数 644、417、388 ms）。D 的字面动作（空载）无法区分产品路径与环境。本对照检验：首次使用一段很短的非空文本时，绘制之后的等待是否仍然出现。

- 夹具不改，只改运行脚本的尺寸：1 KB（1024 字节）与 1 MB（1048586 字节），仍是 attach 模式。1 KB 不超过同步路径阈值（65 536 字节），即时创建视图，没有后台准备，也没有 `fulltext_attach`；1 MB 走后台准备与主线程安装。两者都先有空占位视图，流程与阶段二 C 相同，只差文本路径与大小。
- 脚本结构不变：先跑第一个尺寸的 3 个进程，再跑第二个尺寸的 3 个。奇数 attempt（1、3、5）先 1 KB，偶数 attempt（2、4、6）先 1 MB。进程序号按日志中报告的先后从 1 起。
- 分组（每个作业 6 个进程，共 6 个作业）：

| 组 | 进程 | 个数 | 用途 |
|---|---|---|---|
| 1 KB 冷启动 | 奇数 attempt 的 1 | 3 | 判读 |
| 1 MB 同次冷启动 | 偶数 attempt 的 1 | 3 | 有效性 |
| 1 MB 在 1 KB 之后的首次 | 奇数 attempt 的 4 | 3 | 判读 |
| 1 KB 在 1 MB 之后的首次 | 偶数 attempt 的 4 | 3 | 只报告 |
| 1 KB 热态 | 奇数 attempt 的 2、3，偶数 attempt 的 5、6 | 12 | 基线 W |
| 1 MB 热态 | 偶数 attempt 的 2、3，奇数 attempt 的 5、6 | 12 | 只报告 |

- 冷启动：作业中第一个出现文本绘制的进程。不以 `fulltext_attach` 判断，1 KB 没有该事件。
- 停顿（探针，不依赖事件顺序）：载入步骤中存在一个 episode（最大探针延迟 ≥ 200 ms）。阈值与阶段一、二相同；本调查对停顿的定义以此为准。
- 绘制到 locate（主指标，有门控）：绘制结束到 locate 开始。1 KB 的绘制取创建时间不早于其 `fulltext_request`（字节数 1024）的第一个 `fulltext_first_draw`（创建时刻 = `t_ms` − `milliseconds`）；1 MB 沿用阶段二 C 的取法。门控：绘制结束必须不晚于 locate 开始；locate 缺失也算无定义。无定义的进程不计入绘制到 locate。

预先约定的规则（读取数据前确定）：

1. 冲突时以探针为准。停顿判断只用载入 episode。绘制到 locate 用于定位与报告；两者不一致时在结果中注明，不改变探针的判断。
2. 组的判定（每组 3 个进程）：至少 2 个有载入 episode 为「停顿」；0 个为「无停顿」；其余为「混合」。
3. 无停顿带：W 为同次 1 KB 热态绘制到 locate 的中位数（有定义的进程）。W ≤ 20 ms 时带为 ≤ 50 ms；W > 20 ms 时带为 ≤ 2W。1 KB 冷启动绘制到 locate 的中位数落在带内记为「在基线内」，只作报告。W 无定义时只用探针判读，并注明。
4. 有效性（1 MB 同次冷启动）：3 个中至少 2 个同时满足绘制到 locate ≥ 200 ms 且载入 episode ≥ 200 ms（episode 为交叉核对）。不满足则本次对照作废，不做任何结论，并说明本次环境没有复现停顿。
5. 读数（仅在有效时）：
   - 1 KB 冷启动为「停顿」：非空文本的首次使用开销与尺寸和路径无关，判为环境。
   - 1 KB 冷启动为「无停顿」，且 1 MB 在 1 KB 之后的首次为「停顿」：1 KB 没有耗尽冷启动状态，停顿与后台准备到主线程安装的交接有关，属于产品路径（路线 B），另立产品计划，不判为 D。
   - 1 KB 冷启动为「无停顿」，且 1 MB 在 1 KB 之后的首次为「无停顿」：首次使用的开销在 1 KB 中不可见，结论依赖路径，记为不确定。
   - 其余（任一组为「混合」）：不确定。
6. 失败与缺失：
   - 1 KB 进程缺 `fulltext_locate`（被后续的 prepare 取消）：该次只用探针判读，不算失败。
   - 作业的 6 份报告须可解析，`single_utf16` 等于字节数，无 `FAIL:` 行，1 KB 报告含 1024 字节的 `fulltext_request` 与其后的文本绘制。不满足的作业在结果中注明并排除；每组的实际个数在结果中给出，少于 2 个的组不作判读。
   - 结论查询为空时重试（每次间隔 10 秒，共 5 次）；仍为空则以日志判断（6 份报告、无 `FAIL:` 行）后继续，并在结果中注明。

- 两个尺寸的冷启动中位数都 ≥ 310 ms，满足「归 D」。按预先登记的参照（387.4 ms）与同口径参照（387.7 ms），结论相同。
- 余量：65 537 字节的中位数为 644.2 ms，余量充足。256 KiB 的中位数为 416.7 ms；要使它低于 310 ms，三次中需有两次低于 310 ms。实测只有一次接近（327.8 ms）。
- 「归 B」的条件（两个中位数都 ≤ 194 ms）不成立。六个冷启动中没有一个低于 327 ms。
- 冷启动停顿没有随尺寸增长：65 537 字节的中位数（644 ms）比 1 MB 参照（388 ms）还长。方向与 B 的预期相反，但 n=3，只能说没有随尺寸增长，不能说小尺寸更慢。
- 结论：停顿不随尺寸增长，判为争用或环境，按 C 行转 D。D 行的字面动作见「下一步」。

**观察**

- 冷启动停顿窗口内主线程几乎不计算（CPU 占比 0.07–0.18），以等待态为主，与 1c 一致。热态安装窗口的 CPU 占比为 0.34–0.76。

- 冷启动的安装主体（attach 到首次绘制结束）为 53–131 ms，热态为 9–19 ms，两者都不随尺寸变化。
- 空占位视图的首次绘制（创建到绘制结束，空文本，早于安装）：冷启动 73–173 ms（中位数 115–153 ms），热态 30–63 ms。首次 NSTextView 绘制确有首次使用开销，但小于安装之后的等待：冷启动的绘制到 locate 为 238–617 ms。

- 没有采样，停顿点的调用栈仍然缺失，候选 7 与候选 11 仍未区分。

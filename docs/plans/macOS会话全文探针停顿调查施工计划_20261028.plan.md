# macOS 会话全文探针停顿调查施工计划

## 概要

- 问题：手动探针 `macos/tests/session_fulltext_main.swift` 在同一套 macOS 代码上得到 367.06、244.25、349.23 ms。指标是全程最大主线程延迟，单次停顿即决定 PASS 或 FAIL。
- 目标：找出造成 240–370 ms 停顿的具体操作，并判定它属于夹具、产品还是运行器环境。
- 不做：不放宽 250 ms；不改用 p95 等替代指标；不改产品 Swift 源码；不在本地编译；不改门禁与 publish。
- 状态：计划草案，未执行。阶段一需要一次整轮云端运行，执行前需你确认（见「决策点」D1）。
- 依据：`docs/plans/macOS夹具与打包并行计划_20261027.plan.md` 的「探针与重跑实测」「探针再跑实测」；`git diff --stat b42ab36 e49d656 -- macos` 无输出，即三次结果对应的 macOS 代码相同。
- 实施前提：按 AGENTS.md，任何新 worktree 放在 `$HOME/Documents/Code/Project/Project Worktree/KaneoPilot/<任务标识>/`。

## 已知事实

### 三次结果

| 运行 | 提交 | 主线程最大延迟 | 结论 | 慢采样（≥200 ms） |
|---|---|---|---|---|
| 40475448852 | b42ab36 | 367.06 ms | 失败 | 10 个：367、360、312、304、287、279、264、246、226、207 |
| 40513804568 第 1 次 | e49d656 | 244.25 ms（p95 25.99 ms，566 个样本） | 通过 | 未输出（只在最大值 ≥250 ms 时输出） |
| 40513804568 第 3 次 | e49d656 | 349.23 ms | 失败 | 9 个：349、331、325、277、266、259、241、219、204 |

阈值 250 ms 位于三次停顿长度 244–367 ms 的范围之内。

### 慢采样的形态（推断，待时间戳核实）

- 两次失败的慢采样列表都严格递减。这与一次连续停顿期间排队的采样在停顿结束后依次执行的形态一致。若成立，则每次运行的最大值约等于一次停顿的长度。
- 相邻差值为 6–48 ms，而计时器周期是 10 ms。这说明计时器在停顿期间也可能延迟。日志没有时间戳，无法核实。
- 通过的一次中，p95 为 25.99 ms：大多数样本正常，停顿是少数。

### 已埋点的主线程操作都没有超过 200 ms

第 3 次失败的事件快照（`events`）中，主线程上的埋点操作最大值如下：

| 事件 | 计时范围 | 最大值 |
|---|---|---|
| `fulltext_attach` | `install()` 函数体（`SessionMessageDetailView.swift:495–517`） | 24.46 ms |
| `fulltext_first_draw` | 视图创建到首次 `draw` 结束（`:333–346`，含创建后的其他工作） | 88.71 ms |
| `fulltext_locate` | `scrollRangeToVisible`（`:536`） | 0.66 ms |
| `fulltext_stop` | `stop()`（`:574–587`） | 1.14 ms |
| `fulltext_panel_open` / `_close` | 面板展示与关闭 | 55.23 ms / 4.05 ms |

`fulltext_prepare` 最长 1163.53 ms，但 `main_thread` 为 false，在后台执行。

因此，≥200 ms 的停顿不在这些计时区间之内。这是推断，成立的前提是埋点之外确实有主线程工作；下文的候选正好位于埋点之外。

### 「textkit」标签不代表 TextKit

`probeStage` 只在 `session_fulltext_main.swift:229` 从 `textkit` 变为 `panel`。因此标签 `textkit` 覆盖第 92–228 行的全部步骤：初始大文本、缩放、陈旧代次、Unicode 大文本、Markdown、模式切换、交互与剪贴板。这些步骤里有大量夹具自身的主线程工作（见候选 1–5）。所以「TextKit 对 1 MB 文本的开销」不是首要假设。

## 阶段一：归因（只改夹具，不改产品源码）

改动只在 `macos/tests/session_fulltext_main.swift` 中进行；需要时才改 `run-session-fulltext-fixtures.sh`。

1. 时间戳：`SessionReaderPerformance` 桩的 `record` 与每个探针样本记录 `t_ms`（相对夹具启动的单调时钟毫秒）。
2. 步骤标签：把 `probeStage` 拆成步骤名：载入、缩放、陈旧代次、Unicode、Markdown、模式切换、交互、剪贴板、面板。样本的标签在**触发时**读取，而不是执行时。这样，停顿的起点能对应到开始阻塞的那一步。
3. 直接计时：候选 1–5 的每个夹具调用包进 `timed(label)`，记录同步耗时。
4. 看门狗：一个后台线程，休眠 5 ms，记录唤醒超时（≥50 ms 的时间点与幅度）。它不访问主线程。
5. 环境：夹具启动时输出 `activeProcessorCount`、`getloadavg` 与 `systemUptime`。
6. 报告：PASS 与 FAIL 都输出同一份 JSON。
   - `episodes`：每段 ≥200 ms 的停顿，含起点 `t_ms`、长度、起点步骤标签（取同段内最早触发的样本）。
   - `ops`：每个标签的次数、最大值、总耗时。
   - `watchdog`：超时列表。
   - `environment`。
   - 保留 `probe_max_ms` 与 `result` 字段，便于与历史结果对齐。
   - 耗时断言的阈值与「最大值」口径不变。诊断模式下只记录，不因耗时退出，以便同一作业顺序跑完各模式。

对照模式（同一诊断提交，用环境变量 `KANPILOT_PROBE_MODE` 切换，仅诊断用）：

- `full`：当前全部步骤。
- `attach`：载入 1 MB 文本，等待首次附着与绘制后结束，不做交互。
- `idle`：无文本，只运行计时器与看门狗，时长与 `full` 相当。

运行次数（开始前固定）：

- 诊断提交推送到诊断分支，提交信息加 `[skip ci]`，避免推送即整轮运行。首次使用时核对：推送被跳过，`workflow_dispatch` 仍运行。
- `gh workflow run packages.yml --ref <诊断分支> -f probe_session_fulltext=true` 一次（整轮）。
- 同一提交上 `gh run rerun <run> --job <探针作业 ID>` 两次（各约 41 秒）。
- 每个作业内，`full`、`attach`、`idle` 各跑 3 次。

归因成立的判定（阶段一结束时）：

- 3 个样本中至少 2 个出现 ≥200 ms 的停顿，且起点标签一致；
- 该标签内某个直接计时操作的单次耗时 ≥ 停顿长度的 80%；
- 看门狗结论与该停顿一致（不是进程级）。

满足则进入阶段二 A。起点标签一致但没有直接计时操作能解释，进入阶段一b。看门狗同时超时，进入阶段二 D。标签不一致，记为「未归因」，保留全部数据，并与你讨论是否增加样本。

## 阶段一b：栈采样（仅当阶段一未归因）

- 在诊断提交上让 `run-session-fulltext-fixtures.sh` 在后台启动夹具，并用 `sample <pid>` 采样；输出随日志上传。`sample` 的参数以首次云端运行为准。
- 首次运行需确认 `sample` 在托管镜像上可用。不可用时改用 `xctrace`（Time Profiler，云端执行）。
- 采样会暂停目标进程，可能改变时序。采样样本与不采样样本分开统计；`idle` 模式下的采样结果用于检验采样本身的影响。
- 退出标准：栈帧能指向 `KaneoPilot` 的具体符号或具体的系统框架调用，并能对应到起点标签。

## 决策点

按顺序提问，每项给出推荐：

- **D1 是否开始阶段一（推荐：是）。** 成本：一次整轮运行（上一次整轮墙钟 8 分 34 秒）与两次探针重跑（各约 41 秒）。
- **D2 阶段二归因为夹具时，是否允许修改夹具（推荐：是）。** 只改测试代码，不改产品源码、阈值或指标。
- **D3 阶段二归因为产品时，是否另立产品施工计划（推荐：是）。** 单独文件，本计划不包含产品修复。
- **D4 空载也显著停顿时，指标是否改口径（推荐：先不改）。** 若改，必须先修改 `docs/ui-spec.md` 第 232 行（「关键设计决策 › 5. 局部视觉规格」）：该行要求全部流程按「≥250 ms 停顿阈值」验证，AGENTS.md 要求实现分歧先改规格。不推荐仅以 p95 替代：上一次通过的样本 p95 为 26 ms，却有 244 ms 的停顿，p95 会掩盖这类缺陷。
- **D5 阶段三通过后是否回到门禁（推荐：暂不，先保持手动）。**

# 执行轮结束后的监控补给与评审收尾

## 概要

执行轮已经正常结束，任务却一直停在 running/monitor，进不了评审。StarTool 任务 `kkw1goas3mo7sse8orfo1ibd` 的执行轮于 2026-10-14T18:30:07Z 结束（exit 0），到 2026-10-15 仍是 running。没有任何 monitor 请求去读取结果，所以既没有跑核心验证，也没有进入 in_review，更没有 review 请求。

根因：§4.8 业务周期 tick 已经没有周期调用方。2026-10-12 App 改由 EngineSupervisor 监督 `engine run` 之后，只剩 worker 领取时的内联 tick；队列一旦排空，就没有组件再补建 monitor/review。引擎原有的轮次收尾兜底又信任 `run_status`，而人工接管任务根本不在引擎视野里，两条路都断了。

本计划：

- 引擎每个循环（60 秒）对 live 项目执行一次 §4.8 tick，放在 intake 之后、spawn 之前，同一循环就能拉起 monitor/review worker。
- `tick` 增加可选过滤 `project_ids`；CLI 手动调用和 claim 内联的行为不变。
- 修正 `_round_settle` 的门：只要轮次已退出就补 monitor，不再因为 `run_status` 已是终态而跳过；每轮 2 次的预算保留。
- `engine status` 和 `doctor` 暴露 tick 新鲜度，再出现失联时能直接看到。
- 规格先行：同步 protocol、automation-contract、state-model 中已过时的调度描述。

状态：仅计划，未实施；参数已于 2026-10-15 确认。

**根因**

1. **周期 tick 没有调用方。**
   - §4.8 tick 只在两处执行：
     - `claim` 内联（`cmd_exec.py:255`）：覆盖全部项目，但不传 preflight，所以不做自动确认。
     - CLI `tick`（`cmd_read.py:177–183`）。
   - 提交 `9897791`（2026-10-12）把 `AppRuntime` 里的 `ExecutorScheduler` 换成了 `EngineSupervisor`（`AppRuntime.swift:9`、`:16`）。前者每 20 秒调用一次核心 `tick`（`ExecutorScheduler.swift:143`）。后者只拉起 `engine-run {"mode":"legacy","intake":true,"spawn":true}`（`EngineSupervisor.swift:97–103`），另外每 20 秒跑一次 `recover-execution-goals`（`:146–149`、`:167`），不调用 tick。
   - 引擎对 running 任务的决策是 AWAIT（`decide.py:62`）；`spawn_step`（`loop.py:550–579`）只消费已排队的请求。最后一个 monitor 完成后，内联 tick 因间隔未到不补建；从此 running 任务不再有 monitor，in_review 任务也不会有 review。
   - 规格没有随切换更新：
     - automation-contract「常驻调度与菜单栏」（`:396–425`）仍写"每 20 秒调用核心 tick"。
     - protocol §5.19（`:748–757`）仍在描述 ExecutorScheduler。
     - state-model `:400` 仍写"自动确认由 tick 执行"。
2. **收尾兜底信任 `run_status`。**
   - `_round_settle`（`loop.py:324–388`）的门是 `if not world.get("exited") or world.get("terminal_recorded")`（`:363`）。其中 `terminal_recorded` 就是 `run_status ∈ {finished, failed}`（`rounds.py:69–70`）。
   - `run_status` 只是"最近观察值"（protocol §5.16.1，`:578`、`:588`）。写它的是 worker 自己的收尾和读取层回填（get-session 等），两方都不建 monitor。
   - 结果是：只要 worker 自己写了终态，或者 UI 打开过会话详情触发回填，兜底就失效。这道兜底由提交 `51d43db` 引入（依据 `docs/evidence/sandbox-live-20261010.md` §13.2），它假设"已登记终态 = 不存在登记缺口"，这个假设不成立。`test_engine_round_settle.py:253` 还把这一行为钉成了预期。
3. **人工接管任务不在引擎视野里。**
   - `_candidate_tasks`（`loop.py:187–191`）只取 `is_automation_managed` 的任务（`core.py:309–311`：有 automation 且 `manual_takeover=false`）。
   - 转为人工处理后"按普通手动任务处理"（automation-contract `:464`）。普通手动任务的 running→monitor、in_review→review 本来就只靠 §4.8 tick（`cmd_read.py:29–99`，这两段不区分是否托管）。tick 失联后，接管任务连兜底都没有。
   - monitor 阶段本身能处理接管任务：live 项目 exit 0 → engine-verdict → `_finish_complete` → in-review（`auto_monitor.py:110–174`）；`delivery.mode=manual` 时不提交。缺的只是触发它的请求。
4. **其他恢复路径按设计不负责收尾。** `recover-execution-goals`（`cmd_read.py:144–175`）和 round-observe（`cmd_dispatch.py:834`）只管观察者与续接。job 已 finished 时，round-observe 直接返回 `finished`，不推进（`:910`）。这符合 §5.28.5，本计划不改。

## 关键设计决策

**D1 周期 tick 由引擎执行，不由 App 执行。**
- 引擎是唯一的长驻进程，持有 DB 级租约，同一循环里还负责 spawn。在 spawn 之前 tick，新建的 monitor/review 请求当轮就有 worker 领取。
- 不采用"EngineSupervisor 每 20 秒调用 `tick`"，原因有两个：
  - 不加过滤的 tick 会给 legacy/shadow 项目建请求。引擎拉起的 worker 只领取 live 项目或手动规划请求（`engine_claim_scope.allows`，`:43–56`），这些请求会永远排队。
  - App 不运行、只跑 CLI 引擎时，就没有 tick。
- 不恢复 ExecutorScheduler。

**D2 范围：有效模式为 live 的项目。**
- 口径与 `_queued_stages`（`loop.py:516–530`）和 `allows` 一致：`modes.get(project_id, self.mode) == "live"`；`force` 时用进程模式。
- 不用 `_live_project_ids`（`:128`）。它还要求 enabled 和 preflight 通过，只适合 intake；已经在跑的任务不应因为 preflight 临时失败就失去观察。
- shadow 只计算不写，legacy 不驱动，两者都不 tick，保持 §5.27.7 的三态语义。
- `tick` 新增可选参数 `project_ids: string[]`：
  - 缺省 = 全部项目，CLI 手动调用和 claim 内联的行为不变。
  - 传入时，monitor、review、托管三段都只处理这些项目的任务。`cmd_tick` 的 preflight 也只为过滤范围内、有托管 ready 任务的项目计算。
  - 空列表或含非字符串元素 → `bad_request`。

**D3 引擎步骤与失败隔离。**
- 新增 `Reconciler.business_tick_step(conn, modes)`，在 `reconcile_once` 的 intake（`loop.py:479–480`）之后、spawn（`:482–483`）之前调用。
- 范围：取 `save_state='active' AND status!='done'` 的任务所在项目，再筛出有效模式为 live 的项目。
  - 结果为空时记 `{"action":"business_tick","executed":false,"reason":"no_live_projects"}`，不调用 tick。
  - 否则在 `engine_claim_scope.command_mode(self.mode, self.force_mode)` 内执行 `self.run_command("tick", {"project_ids": sorted(pids)})`，在 actions 里记下 created/skipped 计数和 created 明细。
- 捕获全部异常（不只是 `KanpilotError`），记入 actions 并写 `self.log`，不向外抛。`run()` 只在 `reconcile_once` 成功后才续租（`loop.py:620–628`），所以 tick 出错不能拖垮 spawn 和租约。
- 开关：
  - `Reconciler(enable_tick=False)`：与 intake/spawn 一样默认关闭，保持调度单测隔离。
  - `engine-run` payload 新增可选 `tick: bool`，缺省取 `spawn` 的值。`cli.py:554–557` 的 schema 加 `"tick": (False, "bool")`；`commands.py:137–143` 构造 Reconciler 时传入。
  - App 现有 payload（`EngineSupervisor.swift:97`）不用改就会开启。

**D4 节奏。**
- 每个引擎循环执行一次：`min(lease/3, 60)`，默认 60 秒（`loop.py:610`）。
- monitor 的间隔门不变，仍由 `util.monitor_interval`（`util.py:261–267`）决定：默认 120 秒，存量 900 按 120 解释。running 任务大约每 2–3 分钟被观察一次。
- 和 ExecutorScheduler 时期相比，tick 从每 20 秒一次变为每 60 秒一次；monitor 的实际频率仍由间隔门决定。

**D5 人工接管任务：恢复观察与评审，自动化动作仍跳过。**
- 引擎决策仍不纳入接管任务（`_candidate_tasks` 不变）：不自动确认、不开修复轮、不建 PR 交付、不做 `_round_settle`。
- tick 的 monitor/review 两段本来就不区分托管（`cmd_read.py:29–99`）。恢复周期 tick 后，接管任务重新得到 running→monitor 和 in_review→review，这正是"按普通手动任务处理"的本意。
- 托管段（`:101–138`：丢失租约释放、自动确认、PR 交付补建）仍只对托管任务生效。
- 规格写明：转为人工处理只停止自动化决策，不停止观察、收尾与评审。

**D6 修正 `_round_settle` 的门。**
- `:363` 改为 `if not world.get("exited"): return None`。其余条件保留：
  - 任务仍处于 observe/running；
  - 没有活动请求；
  - `job.json` 身份核验通过，且记录了 `ended_at`/`exit_code`。
- 每轮 `MAX_ROUND_SETTLE=2` 次的收据（`:45`）保留，shadow 照旧不写。`round_exit` 仍返回 `terminal_recorded`，但只作诊断字段。
- 同步改写 docstring（`:325–351`）第 3 条和 `rounds.py:69` 的注释：`run_status` 是观察值，不是收尾信号；收尾的标志是任务离开 observe/running。
- 价值：
  - 托管任务在轮次退出后的下一个循环就会补 monitor，不必等间隔。
  - `tick` 关闭或出错时仍有兜底。
- 与 tick 的交互：同一循环里，settle 先入队 `monitor:<task>`；随后 tick 看到活动请求，记 `skipped: active`。两者靠同一个 idempotency key 去重。

**D7 可观测性。**
- `engine status`（`health.py:162`）的返回值增加顶层字段 `business_tick: {"last_tick_at", "age_seconds"}`，读自 `settings.last_tick_at`。Swift 只解码 `instances`，新增字段不影响 App。
- `doctor`（`cmd_read.py:797`）增加检查 `business_tick_fresh`：
  - 前提：存在活动引擎实例（沿用 `health` 的活动判定口径），并且 live 项目中有 running 或 in_review 任务。
  - 满足前提且 `last_tick_at` 超过 300 秒 → `ok=false`，detail 给出已过去的秒数和处理提示。
  - 不满足前提 → `ok=true`，detail 说明原因。
- 不新增 setting：`tick_inline` 已经在写 `last_tick_at`（`:140`）。这种做法的局限见"风险"。

## 风险

- **观察频率上升。** "存量 900 按 120 解释"由 `8742d5d`（2026-10-13）引入，晚于 tick 失联（`9897791`，2026-10-12）。失联前本机按 900 秒（15 分钟）观察；修复后变成每 2–3 分钟一次。每次 monitor 包含一次 Kaneo 复核，外加若干行 DB 写入。嫌频繁的话，把 `monitor_interval_seconds` 设为 900 以外的值（例如 600）。
- monitor 反复失败而任务仍为 running 时，会按间隔反复观察，这是 §4.8 的既有语义。托管任务另有 settle 预算和阶梯 1 重试兜底。上线后观察，必要时另开后续。
- `lifecycle_owner` 泄漏会让 dispatch/monitor/delivery 的 spawn 一直让行（§5.27.9 已知问题），表现与本问题相似。区别在于 spawn 动作里会出现 `deferred: lifecycle_serial_busy`。
- legacy 项目仍然无人推进，这是三态设计的预期。claim 内联 tick 仍会给 legacy 项目建没人领取的请求（既有行为，本计划不改）。
- verify 预算不超过 monitor 租约的 80%，`connectedE2eAndroidTest` 这类长命令可能超时（既有问题）。
- claim 内联 tick 也会刷新 `last_tick_at`。因此，如果引擎的 tick 每轮都报错、但仍有 worker 在领取，doctor 的新鲜度检查发现不了；这种情况要靠引擎 actions/日志里的 business_tick 错误来发现。

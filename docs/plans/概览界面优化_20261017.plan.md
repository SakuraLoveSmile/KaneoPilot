## 现状问题

1. **同一状态说了四遍，且用了两套阶段词。** 头部「执行中」与「阶段：执行」（`TaskDetailContentView.swift:85-98`）；步进说明「阶段：执行 · 条件：执行中」（`Components.swift:835`）；「当前状态：执行中」「生命周期阶段：监控」（`TaskDetailContentView.swift:905-906`）。「阶段」（observe → 执行）与「生命周期阶段」（monitor → 监控）取值不同，读者会以为有两个阶段。
2. **状态文字自相矛盾。** 徽标写「执行中」，下方写「请求已排队，尚未开始」。两句都对，但没有说明排队的是哪一类请求。
3. **已结束的问答摘要排在首屏。** 它位于步进之后、状态之前（`TaskDetailContentView.swift:737-742`）。已结束的记录是历史，不是当前动作，却占据了首屏的位置。
4. **已结束摘要未达到规格。** §4.17 第 485 行要求「收成一行摘要」，附结束时间，并可展开。实际 `closedSummary` 是标题、状态、元信息三行加展开（`TaskDetailContentView.swift:1407-1425`），「执行问题已回答 · 2 题」与「已回答，继续执行」语义重复。上一计划的实施记录写的是「收成一行摘要」，与代码不符，本计划修正。
5. **阶段入口与页签重复。** 三枚图标按钮加 18pt 标题（`TaskDetailContentView.swift:921-954`），去向与顶部「计划 / 执行 / 评审 / 记录」相同。§4.12 要求概览保留「直达对应页入口」，因此建议改为内联链接，而不是删除（待确认）。
6. **18pt 区段标题过多。** 状态与推进、阶段入口、Kaneo 关联、交付、自动处理共五个。字号受 §3 冻结，只能通过减少区段数量解决。
7. **底栏主按钮是通用文案。** `enqueue` 固定显示「安排下一步」（`TaskDetailContentView.swift:1157-1159`）。规格 §4.1 要求按 kind 显示「安排检查」等。核心的可排队动作没有 kind 字段，Swift 不得从 status 自行推导，否则等于复制了核心映射（见「核心侧待确认」）。
8. **远端状态直出英文原值。** `in-progress` 原样显示（`TaskDetailContentView.swift:960`）。

## 目标形态

单列，顶栏与五段页签结构不变。组与组之间用间距分隔；除 Kaneo 关联与交付 / 自动处理外，不再设 18pt 标题。

```
[需要你处理]    仅在出现时：阻塞横幅 / 规划问答 / 评审卡 → 阻塞证据 → 开放可答的执行问答
[状态]          一段下一步说明（排队时带类别，如「检查已排队，尚未开始」）
                最后更新 13:05:17 ·（仅有值时）自动推进已暂停 · 保存状态
[进展]          阶段步进（只高亮，不再写「阶段：」前缀）
                已回答，继续执行 · 2 题 · 13:05 结束        查看问题与回答
                查看计划正文 · 查看执行会话 · 查看记录与时间线   （内联链接）
[Kaneo 关联]    远端状态 进行中 · 最后核验 13:03:01 · 打开 Kaneo 任务页面
[交付] [自动处理]  保持现有区段与「未开启」文案（规格第 344 行）
[技术详情与路径]  折叠，不变
```

- **需要你处理**：阻塞证据移到问答区之前，保持 §4.17 第 482 行「阻塞证据之后、下一步操作之前」的顺序。
- **状态**：删除「当前状态」「生命周期阶段」两行。排队说明中的类别由 `activeRequest.kind` 做显示映射（plan→规划，dispatch→派发，monitor→检查，review→评审）。无 kind 时沿用原文。仍须保留「尚未开始」，不得写成已开始。
- **进展**：步进条件文字仅在与头部状态文字不同时显示，并写成「条件：…」。已结束的问答收成一行，展开查看只读列表。保留的未保存草稿仍须完整可见。
- **底栏**：结构不变（主按钮、更多操作、只读标签）。

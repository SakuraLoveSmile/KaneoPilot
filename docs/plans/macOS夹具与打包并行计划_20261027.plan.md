# macOS 夹具分片与打包并行施工计划

## 概要

Packages 的 macOS 作业现在是 11 个桌面夹具串行（402 秒），接着构建 DMG（194 秒）。推送后约 10 分钟才能下载到 DMG。本计划回答两个问题：macOS 夹具能否分片（能），以及怎样排才能真正缩短墙钟时间和预览等待。

- 状态：阶段 1 已实施（提交 a42d1f8）。云端构建一红一绿（同一提交，见「实测记录」）；安装与真机验证、正式发布均未做。阶段 2a（两片 + 接入 8 个夹具）已实施（提交 9085aec），云端绿（run 40471213608，见「2a 实测记录」）；2b 未实施。过期的两个夹具已接入（提交 b42ab36）：`run-engine-fix-revert-fixtures` 云端通过；`run-session-fulltext-fixtures` 云端失败（主线程 TextKit 耗时 367 ms，阈值 250 ms），门禁为红，待你决定去留（见「过期夹具接入实测」）。
- 依据：Packages run 40458644157（提交 41c6444，全部作业成功）的作业与步骤耗时；run 40449158214 的排队时间与拆分前的 checks 耗时。
- 范围：`.github/workflows/packages.yml`；`docs/build-release.md` 第 67 行只需核对，通配已能匹配新报告名。阶段 2 另涉及 `scripts/pytest_shards.py`、`scripts/pytest_shard_durations.json` 与 `scripts/tests/test_pytest_shards.py`。
- 不做：不改 Swift 源码与夹具脚本内容；不改 release 门禁与标签流程；不引入自托管 runner。
- 实施前提：按 AGENTS.md，实施者在 `$HOME/Documents/Code/Project/Project Worktree/KaneoPilot/<任务标识>/` 下新建 worktree 后再改动。

## 现状

| 作业 | 结果 | 耗时 | 说明 |
|---|---|---|---|
| identity | 成功 | 5 秒 | — |
| checks 分片 1–5 | 成功 | 340–452 秒 | 测试本体：分片 4 为 440 秒（最慢），分片 5 为 330 秒 |
| macos | 成功 | 608 秒 | 夹具 402 秒 + DMG 194 秒，串行 |
| android | 成功 | 205 秒 | `needs: [identity, checks]`，checks 结束后才开始 |
| publish | 跳过 | — | 非 release |

- 关键路径是 checks（452 秒）→ android（205 秒），合计约 11 分钟。macOS 的 608 秒不在关键路径上。
- 排队：各作业从 created 到 started 为 2–3 秒，可忽略。
- 拆分前 checks 是单作业，耗时 2086 秒（run 40449158214）；分片后约 7.5 分钟。

## 结论

1. **夹具可以分片。** 11 个已接入夹具都用 `mktemp -d` 创建自己的工作目录，各自用 `swiftc` 编译。`run-engine-fixtures.sh` 的 `HOME` 与 `run-owner-fixtures.sh` 的 `KANPILOT_PI_HOME` 都指向夹具自己的目录。不同分片跑在不同 runner 上，跨分片没有共享状态。DMG 步骤（`scripts/build_app.sh`、`scripts/build_dmg.sh`）不依赖 `macos/tests`。
2. **夹具分片本身不省时间。** 最慢的 checks 分片（452 秒）比全部夹具之和（402 秒）还长。只要 checks 不变，夹具怎么分都不会改变墙钟。
3. **真正的收益来自两处：** 把 DMG 拆成独立作业与夹具并行，并让 android 不再等 checks。这是阶段 1：墙钟预期从约 11 分钟降到约 7.6 分钟（实测 8 分 17 秒至 8 分 54 秒，见「实测记录」），DMG 可下载时间从约 10 分钟降到约 3.5–5 分钟（实测）。
4. **夹具分片要和 checks 加分片一起做**（阶段 2）。checks 拆成 8 片后，单片夹具（402 秒）会成为瓶颈；夹具拆成 2 片后最慢一片约 204 秒，低于 8 片 checks 的理论值 258 秒。两者合做后墙钟约 4.5–5 分钟。

## 阶段 1：DMG 独立作业 + android 解耦

改动只在 `.github/workflows/packages.yml`：

1. **`macos` 改名为 `macos-fixtures`。** 保留 checkout、setup-python 3.11 与 "Affected desktop fixtures" 步骤（11 个夹具，逐字不变）。删除其中的 "Build and verify Universal DMG" 与它的 artifact 上传。夹具报告上传名改为 `macos-check-reports-${{ github.run_number }}-fixtures`。
2. **新增 `macos-package` 作业。** `needs: identity`，`runs-on: macos-15`，`timeout-minutes: 45`。步骤依次为 checkout（`ref: ${{ needs.identity.outputs.sha }}`，`persist-credentials: false`）、setup-python 3.11、原样复制 "Build and verify Universal DMG"，再上传两个 artifact：
   - `macos-universal-local-signed-${{ github.run_number }}`，名称与路径不变（publish 按名称下载）；
   - `macos-check-reports-${{ github.run_number }}-package`，内含 `dmg-build.log`。
   同一 run 内同名 artifact 不能重复上传，所以两个作业用不同后缀；两者都以 `macos-check-reports-` 开头，`docs/build-release.md` 第 67 行的通配仍然成立。
3. **`android`：`needs: identity`**，去掉 checks。它的步骤只读 `needs.identity.outputs`，没有其它依赖。
4. **`publish`：** `needs: [identity, checks, android, macos-fixtures, macos-package]`；`if` 中把 `needs.macos.result` 换成 `needs.macos-fixtures.result`，并增加 `needs.macos-package.result == 'success'`。

预期：
- 墙钟约 5 秒 + checks 452 秒 ≈ 7.6 分钟（实测 8 分 17 秒与 8 分 54 秒，偏乐观，见「实测记录」）；
- DMG 工件约 5 + 排队 3 + checkout 2 + DMG 194 + 上传 2 ≈ 3.5 分钟可下载（现状约 10 分钟）；
- 夹具作业原预期约 6.8 分钟，略短于 checks。实测与此不符：红运行的夹具步骤 440 秒，绿运行 508 秒（三个 macOS 作业并行）；正常推送估计约 480 秒，与 checks（427–486 秒）相当，见「实测记录」。

行为变化（需写入实施记录）：
- 夹具失败时，DMG 仍会构建并上传（现状要等 11 个夹具全部通过才产出）。发布门禁不变：publish 仍要求全部作业成功，不会误发布。
- checks 失败时，调试 APK 仍会构建（同样不影响发布）。
- 因此，红色运行里的 DMG 只适合看界面；验收以同一 run 的 `macos-fixtures` 结论为准。

## 阶段 2（可选）：夹具 2 片 + checks 8 片

实测之后，正常推送的夹具步骤约 480 秒（估计），与 checks（427–486 秒）相当，所以 2a 由「可选」变为「建议」。2a 把夹具移出关键路径，墙钟回落到由 checks 决定的约 8 分钟；压到约 5 分钟还需要 2b。若接入 8 个通过的未接入夹具，夹具总量约 744 秒（402 + 342）：2 片约 379 秒、3 片约 250 秒、4 片约 194 秒（按 LPT 粗估，未计并行争用）。因此接入这 8 个之前必须先做 2a，否则夹具会远超 checks。届时分组由耗时表重新生成，不沿用下面的两组。

### 2b checks 8 片，core 与 integration 合并均衡

- 现状：core 与 integration 各自均衡，结果分片 4 为 440 秒、分片 5 为 330 秒。

- 理论最大值（旧耗时表）：8 片 257.7 秒，6 片 343.6 秒，5 片合并后 412.3 秒。

预期：墙钟约 4.5–5 分钟。checks 8 片约 270 秒为瓶颈，夹具 2 片约 216 秒，DMG 与 android 约 205 秒。

只使用云端构建的 DMG，不在本机编译（AGENTS.md）。以下步骤未在本机执行过。

1. 下载：`gh run download 40467373440 -R SakuraLoveSmile/KaneoPilot -n macos-universal-local-signed-39 -D <临时目录>/download`。这是绿色运行的工件，与红色运行同为提交 a42d1f8 的构建；保留 14 天。

4. 复位：删除 `fake-state.json`，假核心恢复罐头数据。

限制（已核对代码，未在本机验证运行效果）：
- `KANPILOT_APP_SUPPORT` 在应用内只由 `MCPServiceManager.swift:53` 读取。不设置时，应用与核心都使用 `~/Library/Application Support/KaneoPilot`（`core/kanpilot/constants.py:276`）。
- 应用偏好（UserDefaults）不受上述变量隔离。DMG 的 bundle ID 是 `local.kaneopilot`（`macos/KaneoPilot.xcodeproj/project.pbxproj`），与已安装的同 ID 版本共享偏好，例如 `executorSchedulingEnabled`。MCP 开关的键按支持目录区分，设置 `KANPILOT_APP_SUPPORT` 后不共用。未找到可靠的偏好隔离办法。
- 不要把 DMG 装入 `/Applications`，也不要去掉 `KANPILOT_CORE`：否则会读写真实库 `~/Library/Application Support/KaneoPilot/kanpilot.db` 并启动真实引擎。
- 应用为 ad-hoc 签名、未公证。gh 下载的文件不带隔离属性；浏览器下载的副本可能被 Gatekeeper 拦截（未验证）。

- **红的一次：原因未定。** UTC 2026-10-27 07:21:11，`run-owner-fixtures` 的 `disabled-maintenance` 模式在启动约 0.42 秒后触发 `owner_lifecycle_main.swift:130` 的 `fatalError`（「failed exit read must retain sleep activity with empty known ownership」）。这不是超时：轮询最多等 3 秒（150 × 20 毫秒），但循环只等两个条件（停止存活，且错误含 `fixture stage-exit status unavailable`）。断言还要求 `ownedWorkers` 为空、`preventsIdleSleep` 为真，循环没有等这两个。`status?.ownedWorkers?.isEmpty == true` 在 `status` 或 `ownedWorkers` 为 nil 时也为假，日志无法区分是哪一条失败。
  - 两种可能，均未验证：(a) 夹具问题：循环等待的条件与断言不一致；(b) 产品问题：`ExecutorScheduler` 中 `error` 与所有权、防休眠（`activity`）的更新顺序可能不一致。「失败的退出读取必须保留防休眠与空所有权」是产品不变量，不应按夹具噪声忽略。未核对完整顺序。

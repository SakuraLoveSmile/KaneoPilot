# 执行期提问转交调度台（Plus × KaneoPilot）

## 概要

Plus 执行会话固定为 `goal/auto`，交互模式为 interactive。会话在目标契约轮或执行轮调用 `asktool` 时，问题只出现在 Plus 界面卡片上，KaneoPilot 既看不到也无法回答。执行 worker 会把轮次一直当作"运行中"，直到 4 小时时限触发 stop→abort。stop 会让 Plus 把未答问题全部按"跳过"交给模型，轮次以 `timeout` 失败。

本计划同时修改两个软件：

- 问题出现后在 KaneoPilot 的收件箱、任务详情和系统通知中显示。
- 用户在 KaneoPilot 回答后，答案经核心命令送回**同一 Plus 会话的同一待答请求**，模型在原 turn、原工具调用处继续执行。此后的监控、验证、Review 和交付沿原流程自动推进。
- Plus 界面仍可作答，以先答者为准。
- 问题与答案只经核心固定 JSON 命令和稳定 DTO 交互，为后续手机端预留。按 AGENTS.md 边界，本期不做手机端和远程访问。

状态：实现中。2026-10-14 用户授权按计划实施，待定参数采用推荐值；同日确认前置体验，并授权两仓前置提交及合并。新功能保持不提交、不推送、不安装正式 App、不启动正式任务、不调用付费模型。

## 现状与根因

锚点：KaneoPilot `4e77fab`，Plus `40e32b0a2`。

**Plus**

1. asktool 的等待是 sidecar 内存 waiter（`packages/agent-runtime/src/ask-tool-inputs.ts`），没有超时。turn 被停止时，剩余问题全部按跳过处理（`docs/spec/03-runtime/17-asktool-questions.md` §3）。
2. MCP 控制面经 `pi_desktop_invoke` 能调用 `agent/askTool/resolve`（`mcp-control.ts:251`，dangerous，需要 `confirm`），但没有任何列出待答问题的入口。IPC 已有 `pendingInteractive`，却没有进入 `CONTROL_OPERATION_SPECS`；`pi_agent_status` 也不含待答信息。外部客户端拿不到 `requestId`，所以无从作答。
3. 所有回答都记为 `DESKTOP_PRINCIPAL`（`agent-host-bridge.ts:71`），无法区分外部来源。

**KaneoPilot**

4. 观察循环（`pi_desktop_worker.py:1477–1560`）每 2 秒读取 turn、status 和转录，看不到待答问题。时限（`:888–892`，默认 14400 秒）一到即执行 `agent_stop`（`:1491–1500`），10 秒后 `agent_abort`（`:1523–1535`），最后以 `timeout` 收尾（`:1562–1571`）。结果是先空等 4 小时，再替用户拒答。
5. 现有续接预算按 `started_at + 时限` 计算（`:770–776`、`:945–951`），等待用户的时间也计入其中。
6. 核心没有"执行中需要回答"的状态：attention 的 13 个 reason_code（protocol §5.27.3）中无此类。`answer_plan_questions` 只服务规划澄清（`derive.py:577`、`plan_answers.py`），答完会重新规划，而不是回到原会话。
7. runtime 域（`mcp_tools.py` 的 `_runtime_guard`/`dispatch_tool_call`、`mcp_scopes.py:91–106`）没有列出或回答输入的工具。
8. `round-observe` 的 Goal 续接门只接受 `execution_failed`（`cmd_dispatch.py:846–852`）。自动化段时长预算（`core.py:408–417`，默认 240 分钟）按墙钟计算，用户等待会在 intake、修复轮或自动补救时触发 `auto_budget_exceeded`。

## 关键设计决策

**D1 实时转交，执行会话保持 interactive。**
不采用另一种做法：执行也走 unattended 硬拦截，答完后用新 prompt 续接。那样需要闭合悬空的工具调用、定义 Goal 续接语义，Plus runtime 改动重；Plus 界面也无法再直接作答，模型还会丢失提问时的上下文。本方案只给控制面增加一读一写两个入口，模型在原调用处拿到答案。执行 prompt 不改。

**D2 问题身份与先答者为准。**
- 身份为 `(session_id, request_id)`，附带 `turn_id` 和 `tool_call_id`。
- Plus 对已不再 pending 的 requestId 返回 `ASKTOOL_NOT_FOUND`，天然保证至多一次。新工具把它映射为结构化的 `not_pending`，不作为错误。
- KaneoPilot 不声称本地锁能阻止 Plus 界面同时作答，只做幂等和对账。
- KaneoPilot 对规范化后的问题计算 `questions_sha256`，用来把草稿和提交绑定到问题版本。这个值不传给 Plus，避免两种语言各自定义规范化 JSON。

**D3 发现问题：两段读取。**
- worker 每次轮询本来就读 `pi_agent_status`，从中取 `pendingInputs.count/requestIds`。
- 出现新的 requestId 时，再调用 pending 取详情，并核对 `turnId == job.turn_id`；`turnId` 缺省时改用 `status.currentTurnId` 核对。
- 目标契约轮（批准前）和执行轮同样覆盖。
- 详情校验复用硬拦截分支 `plus_interaction` 的上限：20 题、每题 100 个选项、64 KiB、调用 ID 512 字节。不合法或超限的问题仍然阻塞任务，但标记 `answerable=false`，提示"请在 Plus 中回答"，绝不自动代答。

**D4 状态：任务转为 `needs_user`，轮次保持 running。**
- 新增 `failure_code=execution_input_required` 和 `reason_code=execution_question`（阶梯 3）。`attention_id` 沿用 `attn_<task>_<reason>`。
- 不另设子状态，理由有两点：attention-list、通知和后续手机端都以 `needs_user` 为准；engine 的 decide 对 `needs_user` 执行 BLOCK，等待期间不会对该任务做别的事。
- 答案送达后，任务在同一 run 上回到 `running`。先例是 `observation_blocked` 的自动解除（`cmd_exec.py:768–786`）。
- `round-observe` 的 §5.23.8 解除逻辑不得清除此阻塞。

**D5 允许的动作。**
- 问题未关闭期间只提供三个动作：
  - `answer_execution_questions`（推荐）。
  - `skip_execution_questions`：全部跳过，交执行端自行决定，对应 Plus 的 Decline all。
  - `stop_execution`：停止本轮，需二次确认。
- 此期间禁用 dismiss / retry / replan / mark_done，因为 Plus 会话仍活着，开新轮次会出现两个执行者。归档由 `archive_blocked_reason` 拦截。
- 停止后走既有 `execution_failed` 恢复流程。

**D6 送达：收据先行，结果未知时不自动重发，对账只读。**
`submit-execution-answers` 分三步：

1. 短写事务：校验身份与答案，置 `delivery=submitting`。
2. 事务外：经 runtime 域 `kp_runtime_input_respond`。该工具按 §5.25 先 `reserve_downstream` 登记收据，再调用 Plus `pi_asks_resolve`，调用期间不持有 SQLite 写锁。
3. 再一个写事务处理结果：
   - `answered`：清除阻塞，任务回到 running。
   - `not_pending`：读取 status，判断是"已在 Plus 作答"还是"turn 已结束"。
   - 传输结果未知：置 `delivery=unknown`，任务保持 needs_user。

结果未知时不自动重发，由 worker 下一轮轮询或 `reconcile-execution-question` 只读 Plus：

- requestId 已消失：按已作答结算。
- requestId 仍 pending：只能说明该次读取尚待答，保留 `unknown`，不能证明在途原调用未生效。用户显式重试仅相同冻结答案、新 operation_id；有确定未应用证据才置 `not_applied`。

Plus 保证至多一次，所以重复提交最多得到 `not_pending`，没有副作用。

**D7 等待期间的时限。**
- 等待时长以核心记录为准：同一 run 待答集合的等待区间并集（多个问题重叠不重复计时）。worker 的 `job.input_wait_seconds` 只是观察期间的缓存；`round-observe` 续接时把核心累计值带入续接参数。
- 有未关闭问题时，worker 顺延 deadline，绝不 stop 或 abort。
- `_round_remaining_seconds` 和 round-observe 的"已超时"判断都扣除等待时间。
- 自动化段时长预算同样扣除本段等待时间；成本预算不变，因为等待不产生费用。
- 最长等待默认 24 小时，可配置，0 表示不限。到期后 worker 按既有 stop→abort 顺序停止本轮，原因记为 `execution_question_expired`。
- scope 到期时按 §5.25 既有规则以同一身份重新注册。

**D8 关闭与孤儿问题。**
- 问题消失、turn 仍在运行：先核对持久 turn 与身份，仍 running 才按"已作答"结算；completed 时读取完整转录，同 session/turn/toolCallId 的 toolResult.details.resolutionKind=answered 证明真实答后快速结束，可正常结算；stopped/aborted/error 或无证据才按过期结算。来源由核心按送达记录判定：已接受记为 kaneopilot；没有送达记为 plus；送达未知记为 unknown。随后清除阻塞，回到 running。
- turn 已终止但问题仍未关闭（Plus 重启、在 Plus 中停止、出错）：标记 `expired`，核心同事务进入既有 `execution_failed` 恢复；不能仅关闭 DTO 而保留 `execution_input_required`。问题和草稿保留供查看。
- 把答案草稿带入续接依赖 Plus 的 `goal-blocked-resume`，列为二期。

**D9 不依赖 engine 模式。**
- 报告、送达和状态切换都在核心命令和 worker 内完成，不依赖 engine 的 legacy/live 过滤，也不依赖 desktop_queue 领取（这是"未交给 Plus 执行"一事的教训）。
- 观察者退出时有三条恢复路径，都复用既有只读、去重的 `round-observe`：
  1. 提交命令在送达后确保有观察者。
  2. engine 对 `execution_input_required` 且观察者已退出的任务下发 round-observe 意图。
  3. 任务详情提供"重新连接"。

三入口汇入同一普通只读 observer ensure，原子 launch reservation 防并发重复拉起；App 后台 recover-execution-goals 补齐 legacy/shadow/engine 关闭恢复。活跃 ask 不传 continue_goal_only，不扩大 Goal 批准权限或只读写权限。该 run 有问答历史、任务 running 且观察者缺席仍由后台检查；已答后契约轮审批保留既有精确 continue_goal_only 门。
- round-observe 的 `continue_goal` 门放行同一 run 的 `execution_input_required`。

**D10 问题与答案映射。**
- Plus → KaneoPilot：
  - 题目 id 为 `q<i>`，选项 id 为 `o<j>`，`label/description` 保留原文。
  - 新增 `multi_select` 字段，仅用于执行问题 DTO；`plan_questions` 的 schema 不变。
  - `allow_custom=true`，`required=false`（Plus 允许逐题跳过）。
- 回送：
  - 跳过的题目回送 `null`。
  - 其他题目按顺序回送所选选项的原始 label；有自定义文本时追加一项。
  - 单选自定义与选项互斥，最多一个值；多选去重并保持原选项顺序，可追加自定义（总条数仍不超过100）。
- 硬拦截方案中多选退化为文本框，这里不沿用，因为答案要以 `string[]` 结构回到模型。

**D11 审计与隐私。**
- Plus 新增 `MCP_CONTROL_PRINCIPAL`（subject `mcp-control`，role `controller`，具备 `input/respond`），`input.resolved.by` 因此能区分来源。通用的 `pi_desktop_invoke(askToolResolve)` 同样改记这个 principal。
- KaneoPilot 事件记录 operation_id、问题指纹、答案摘要和作答端。
- 不输出、不持久化任何 token。答案作为用户内容存入 task extra；超出上限时明确拒绝，不截断。

**D12 为手机端预留。**
- `attention-list` 的条目增加 `question_preview {count, first_title, request_id}`；通知用 attention_id+request_id 去重，attention_id 稳定契约不变。
- `task-detail` 和 `session-view` 提供完整的 `execution_question` DTO（见附录 A）。
- 写入只经 save / submit / reconcile / stop 命令。
- Swift 只是消费者之一。DTO 冻结在 protocol 新节中，之后只做增量。

## 验收标准

1. 执行轮（包括目标契约轮）出现 asktool 后，10 秒内 KaneoPilot 收件箱出现条目并发出系统通知；任务详情能看到全部题目和选项。
2. 在 KaneoPilot 作答后：
   - Plus 卡片消失，同一 turn 继续。
   - 模型收到的工具输出为"问题：答案"格式（spec 17 §4）。
   - 任务回到 running，之后自动推进。
3. 在 Plus 作答后，KaneoPilot 条目在 2 个轮询周期内消失，事件注明"已在 Plus 回答"。
4. 两端同时作答时恰好一份生效，另一端看到"已被回答"，任务不进入错误态。
5. 送达结果未知时不自动重发，对账结论正确；重新提交无副作用。
6. 等待 6 小时（假时钟）既不触发轮次超时，也不触发 `auto_budget_exceeded`；到达最长等待后以 `execution_question_expired` 收尾。
7. Plus 重启，或在 Plus 中停止时，问题标记为过期，任务进入既有执行失败恢复流程，草稿保留。
8. 引擎停止时回答仍能送达，观察按既有规则续接。
9. 日志、数据库和事件中都没有 token；旧轮次的恢复行为不变。

## 风险

- sidecar 重启会丢失 Plus 的内存 waiter，这种情况只能按过期处理，无法恢复原调用。
- 观察者退出期间，KaneoPilot 感知不到 Plus 端的作答。靠 engine 续接意图和"重新核对"弥补，会有分钟级延迟。
- 长时间等待会占用一个 Plus 会话和一个 worker 进程，开销不大。scope 过期后按既有规则重新注册（P2 验证项）。
- 答案是用户输入，会直接进入模型上下文，信任级别与在 Plus 中输入相同。手机端的鉴权留给手机端方案解决。

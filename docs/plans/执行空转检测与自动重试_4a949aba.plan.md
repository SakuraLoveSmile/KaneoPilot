## 概要

## 关键设计决策

整体流程（标 [新增] 的是本计划新增的环节）：

```text
执行轮结束（completed, exit 0）
  └─ monitor：[新增] 空转？ ── 否 ──> 验证证据（[新增] 只认 goal_approved 之后）──> 交付提交 ──> in-review
        │是
        └─ report needs_user / execution_noop                                   [新增]
              └─ core.cmd_report：[新增] 有资格自动重试？
                    ├─ 是 ──> exec_retries = 1 ──> ready ──> dispatch（备用模型）──> 新一轮执行
                    └─ 否 ──> 停在 needs_user：重新执行 / 重新规划 / 登记完成 / 忽略
```

### 1. `execution_noop` 是独立失败码，不并入 `no_changes`

| | `no_changes`（已有） | `execution_noop`（新增） |
| --- | --- | --- |
| 阶段 | delivery（提交阶段） | monitor（终态观测后、验证前） |
| 含义 | 验证通过后发现没有可提交改动 | 执行轮结束但什么也没做 |
| 可用动作 | replan、mark_done、dismiss | resume（重新执行）、replan、mark_done、dismiss |
| 界面文案 | 「执行未产生改动」 | 「执行空转」 |

两者共用同一个“有效改动集”判断（WP2），保持语义一致。`execution_noop` 加入 `constants.AUTOMATION_FAILURE_STAGES`（`:457-463`），阶段为 `monitor`。

### 2. 判定：改动集优先，回复形态为辅，先于验证

- 信号 A（仅 PR 交付）：有效改动集为空。
- 信号 B（任意交付模式）：最终回复修剪后少于 16 个码点，且执行轮内没有只读白名单之外的工具调用。未知工具名按“有动作”处理，宁可漏判，不误判。
- 任一成立即判空转，判定位置在 `auto_monitor._complete` 里 `_verification` 之前（`auto_monitor.py:99-103`）。
- 只读白名单从本次事件夹具里的真实工具名派生（`UpdateGoalProgress`、`Glob`、`Read` 等）；Plus 真实的写类工具名未经核实（见“未验证项”）。
- 监控只上报，不自己决定重试。事件和标记只记信号种类、计数、回复长度，不记回复正文、命令或路径。

### 3. 重试在核心里同事务完成

`cmd_report` 的 `needs_user` 分支（`cmd_exec.py:572-589`）在 `core.block_task` 之后，若 `failure_code == "execution_noop"` 且任务有资格，调用新增的 `core.start_exec_retry_inline`（仿 `start_fix_round_inline`，`core.py:349-367`）。资格：自动化管理、项目策略开启、`exec_retries < 1`、`automation_budget`（`core.py:337`）通过。同一事务内：

1. `exec_retries += 1`；
2. 重置发送字段 `sent`、`send_state`、`sent_at`、`lock_retained`；
3. 移除 `verification_override`；
4. 保留已确认的计划，不重新规划，不改 `plan_sha256`；
5. 写标记 `extra.automation.exec_retry = {n, reason, from_run_id, model, at, actor}`；
6. 转 `ready`，并自己创建 dispatch 请求（tick 的自动确认只对带 `extra.plan_execution_hold` 的任务生效，`cmd_read.py:112`，不能指望它；建请求的方式施工时在 `confirm_plan_inline`（`cmd_queue.py:24-36`）与 `_new_cycle_request`（`cmd_queue.py:212`）之间选）；
7. 写事件 `exec_retry_started`。

不满足资格则保持 `needs_user / execution_noop`，等用户处置。

### 4. 重试预算独立于修复轮

- `exec_retries` 自动最多 1 次；手动按钮随时可点，点一次累加一次，每次都弹确认。
- 每个修复轮、每次用户重新规划把计数清零。
- 自动重试需 `automation_budget` 通过。Plus 成本是 unknown，实际受 240 分钟时间上限约束。手动重新执行由用户显式触发，不受 `exec_retries` 上限限制，预算口径照 `cmd_queue.py` 里 `auto_budget_exceeded` 的 resume 现有处理（施工时对照确认）。
- 与 Review 的 2 个修复轮分开计数，互不占用。

### 5. 备用模型：配置覆盖，失败即停，不静默切换

- 配置形状：`exec_config.pi_desktop.fallback = {provider_id, model_id, thinking_level}` 三个字段；`connection_file` 与 `permission_mode` 继承主配置；不含 token。
- `exec_config.py` 的块规范化（`:102-127`）和保存校验（`:569-598`）认该子块；`set-exec-config`（`cmd_config.py:39`）可写，`get-exec-config` 回传。
- 使用：重试标记里 `model == "fallback"` 时，`dispatch_validate.py:194` 改用 `exec_config.snapshot(conn, config_override=…)`（`exec_config.py:141-146` 已支持），覆盖内容是主配置加备用三字段并置 `model_source=custom`。快照在 claim 时冻结（`cmd_exec.py:363-366`），实际使用的模型记入 dispatch 事件和轮次快照。
- 可用性：沿用失败即停的探针（`dispatch_validate.py:205`、`cmd_dispatch.py:609`）。备用模型不可用 → `validation_failed`，任务留在待处理，不再悄悄换别的模型。
- 手动入口可选 `exec_model: primary 或 fallback`（`resolve` 载荷），默认备用模型；未配置备用模型时只能选主模型。
- 同步改写 `dispatch_validate.py:189-193` 注释和 `cmd_config.py:39-45` 文档串里“不自动换模型”的措辞：除“空转重试使用用户预先配置的备用模型”这一窄例外外，仍不自动换模型。

### 6. 验证证据窗口

自动化轮的证据只认 `goal_approved` 系统事件之后的工具结果（`protocol.md:1014` 的 `job.goal_approval.execution_turn_id` 可交叉核对）。标记缺失时退回整轮，并在验证证据里记录 `evidence_window`（`after_goal_approved` 或 `whole_round`），让回退可见。

### 7. 目标契约文件的处理

“有效改动集”排除未跟踪、普通文件（非符号链接）、路径恰为 `.pi/goal/<name>.md`（3 段）、且 `.pi` 与 `.pi/goal` 两级父目录都不是符号链接的条目；已跟踪文件的改动一律保留。默认不提交该文件。

不采用 `.git/info/exclude`：在关联工作树里它解析为主仓库的 exclude 文件（已验证），会改变用户主检出的状态。

### 8. 重试与远端状态

首次派发时 `begin_send` 已把远端置为 in-progress。重试标记存在时：

- `core.expected_remote_slugs` 额外接受 `in-progress`；
- `begin_send` 发现远端已是 in-progress 就不再写远端，只读取核验（Kaneo 同状态 PUT 的行为未验证，这样绕开）；
- 核验不符仍按 `remote_conflict` 阻塞。

### 9. 监控间隔：读取时解释，不改数据

库里的 `monitor_interval_seconds` 当前是旧播种值 900。`protocol.md:399` 明确没有 set-settings 命令，所以 900 只可能是旧播种值。用一个读取辅助把“恰为 900”按 120 解释，其余值原样返回，比照 `protocol.md:1925` 对旧 `ask` 的处理方式。不重写数据，不新增“终态立即检查”的触发。

## 风险与规避

| 风险 | 规避 |
| --- | --- |
| 本来就不需要改代码的任务会被判空转，多花一次重试 | 最多一次；原流程里 `no_changes` 同样会拦下它；重试后仍空转即交给用户，可「登记完成」 |
| 备用模型不可用或未配置 | 不可用 → `validation_failed`，留在待处理，不静默换模型；未配置 → 沿用主模型重试一次（默认，待确认），并提示配置 |
| 短回复阈值（16 个码点）误伤极简但合法的回复 | 只在“同时没有写类工具调用”时成立；未知工具名按有动作处理；阈值进规格评审，可调 |
| 重试与远端状态不一致 | 仅重试标记存在时接受 `in-progress`；`begin_send` 只读核验、不做同状态写入；不符仍按 `remote_conflict` 阻塞 |
| 目标文件排除规则过宽，放走真实改动 | 只排除未跟踪、普通文件、固定 3 段路径、父目录非符号链接；已跟踪改动一律保留；测试覆盖越级和链接 |
| 自动重试没有成本数字 | Plus 成本为 unknown，实际受时间上限约束；事件记录重试次数与模型，便于复盘 |
| `plus_status` 修复改变其他消费者的行为 | `is_running` 保持布尔，`raw_status` 不变；消费者（`runtime_client.py:316, :457-462`、`mcp_tools.py:986`）按嵌套优先解包；既有夹具继续有效，另加嵌套样本契约测试 |
| 在 15 个已有未提交改动的文件上叠改 | 见“实施顺序与前置” |

## 功能与使用流程

### T1：项目与仓库

1. 用户进入“设置 → 项目与仓库”，先看到已保存/旧版继承映射，不依赖联网；点击“获取 Kaneo 项目”后，用现有凭据只读获取当前工作区项目。
2. 列表合并远端项目与已保存映射，以 `project_id` 区分身份。未配置项目也显示，用户无需自行填写 ID；同名项目附短 ID，完整 ID 可展开复制。
3. 选中 `StarTool` → “选择目录…” → 显示规范化的完整路径及目录/Git 状态 → “保存”。页面明确：仅用于之后新建的规划输入，已有排队/执行轮次继续使用原快照。
4. 规划列表里不可选的项目给具体原因及“配置仓库”入口，打开同一个 `ProjectMappingsView`，定位项目。配置保存后关闭该配置浮层并刷新 To Do；保留规划面板已选任务、补充说明、本地附件、排除列表，仍符合条件的任务保留选中。
5. 停用与解除映射只改变未来规划资格。停用保留路径；解除保留一个未配置记录，不回落成旧常量、也不删除仓库、任务、材料或历史。保存前显示已排队/执行的数量和影响说明。

| 状态 | 展示与操作 | 对新规划的效果 |
| --- | --- | --- |
| 未映射 | 橙色“尚未选择仓库”+ 选择目录 | 不可准备/排队，给配置入口 |
| 可用目录 / Git 仓库 | 路径 + 状态文字；启用新规划可切换 | 映射及任务状态满足条件时可准备；运行端额外要求在排队前校验 |
| 已停用 | 路径保留、“已停用新规划” | 新规划被拦截；不取消旧请求 |
| 目录不存在 / 不可读取 | 具体错误 + 重新选择目录 | 不把保存成功等同于当前可用；不启动模型 |
| 远端获取失败 | 保留本地列表与编辑草稿，显示错误、重试 | 不显示为“没有项目”；不得用猜测名称/ID 创建映射 |
| 保存失败 / 配置冲突 | 保留草稿、显示错误；冲突提供重新读取 | 不部分保存，不默默覆盖另一窗口的修改 |

## 关键设计决策

### 1. 项目 ID 是身份，名称是展示，仓库是用户选择

- 不再以 `project_name` 决定白名单或本地目录。当前仍只服务一个既有 Kaneo 工作区，工作区 ID 取本地已有设置；不加入工作区切换功能。
- 新模块 `core/kanpilot/project_config.py` 负责读取有效映射、保存及本地路径检查；复用 `db.get_setting/set_setting`、现有 `Bridge Client` 和 JSON 命令风格。不新建配置文件、第三方依赖或配置服务。
- 映射存入 `settings.project_mappings`：`{version:1, revision:<整数>, workspace_id:<当前工作区>, items:{<project_id>:{project_name, repository:<绝对路径|null>, enabled:<布尔>, updated_at}}}`。无需增加数据库表或 schema 版本，不为此运行数据迁移。
- 未保存该键时，旧 `PROJECTS` 转换为按 ID 索引的只读默认映射，路径沿原 `repos_root/name`，`revision=0`。第一次配置写入将完整有效集合写入 SQLite；之后仅以保存集合为准。停用/解除不会重新启用旧映射。GET 不隐式写配置。
- 远端最新名称用于界面展示和之后新建的规划快照；已有计划/任务名称快照不批量改写。同名项目可关联不同仓库；多个项目指向同一仓库允许保存，给普通提示，不按名称合并身份。
- 路径支持空格、中文及 `~` 输入，core 统一展开并规范化成绝对路径。新增/更换路径或启用时要求现有、可读取的目录；停用一条路径未变的已有映射或解除映射不受目录已失效阻止。Git 子目录选择规范化到可查明的仓库根并在保存前展示，普通目录则保存规范化目录。目录符号链接按最终真实路径登记，后续若登记路径变成指向另一目录的符号链接，重新解析与登记值不符就拦截。
- 允许保存普通目录，显示“普通目录”。选择 Plus 等要求 Git worktree 的运行端时，提交规划前明确拦截非 Git 路径；不得自动 `git init`、建库、移动目录或改用户仓库。检查只用只读 filesystem/Git 查询，参数列表调用，不把名称/路径拼进 shell。
- 已保存远端项目消失时标“远端未找到（上次获取结果）”，保留映射和历史，不能自动删除或按同名项目重绑。

### 2. 设置命令与规划阻塞共享同一契约

以下为**待实现的新接口**；沿现有错误码和退出规范，不新增一套错误系统。

| 命令 | 输入 | 输出与规则 |
| --- | --- | --- |
| `get-project-mappings` | `{refresh_remote?:bool=false}` | `{revision, workspace_id, items:[...], remote:{status:"not_requested"|"ok"|"error", fetched_at?, error?}}`；默认只读本地。显式刷新才调用当前工作区 `bridge.project_list`，只 GET，不抓全项目任务；网络失败保留本地 items 并明确 remote.error |
| `set-project-mapping` | `{project_id:str, repository:str|null, enabled:bool, expected_revision:int}` | `{revision, item, deduplicated:bool}`；新建/启用映射先在事务外只读核对该 ID 属于当前工作区，名字由 core 获取；已知本地记录的停用/解除允许离线。事务内复核 revision 后保存单项和 `project_mapping_updated` 事件 |

`items` 每项含 `project_id/project_name/repository/enabled/origin`、本地 `mapping_state`（`unmapped/available/disabled/missing/unreadable`）、`repository_kind`（`git/directory/null`）、`blocked_reason`、`active_task_count/active_request_count`。`origin` 为 `legacy/saved/remote_only`。任务数统计该项目活跃看板中未完成任务，请求数统计其 `queued/claimed` 请求（失联仍属 claimed，不重复计数）；按“未完成任务/活动请求”标注，不把数量误称为正在执行数。这些检查描述本地目录与配置，不能声称模型或远端任务可执行。清除映射必须传 `repository:null, enabled:false`；空字符串不冒充解除。

- 无效 ID/字段为 `bad_request`，非法或不可读取路径为 `validation_failed`，未找到所选远端项目为 `not_found`，网络失效为 `remote_unavailable`，revision 不符为 `conflict`。UI保留 core 原文。禁止返回凭据或连接文件内容。
- 同一项的规范化值完全相同则幂等返回，不新增事件/revision；若发生其他实质修改且版本过期则冲突。网络校验不持有 SQLite 写锁，事务内还要复核工作区和当前配置。
- 在 `fetch-todos` 项中增加可选 `mapping_state/repository_kind/mapping_project_id`，保留既有 `selectable/blocked_reason/repository`。只有映射原因可显示配置快捷入口；发送不明、归档、在执行等任务状态原因仍给相应处理入口，不能错误推荐改仓库。
- 从列表、prepare 到 start 共用按 `project_id` 的有效映射解析。列表核对 task_context 中的项目 ID 和枚举项目 ID；不一致则该项不可选。仓库无效尽早拒绝，不能下载完附件才发现项目未映射。
- GUI 只能经 `CoreClient` 调这两个命令，不直接改 SQLite。映射写命令为桌面/本机用户配置入口，不加入模型的 `kp_task_*` 工具或扩大 task grant 权限。

### 3. 配置变化不能换掉正在使用的仓库

- 新 `prepare-plan-input` 从有效映射取得 `project_id/project_name/repository`，加上 `project_mapping_revision` 写进 `manifest.task`，纳入现有 `input_sha256`。snapshot 的显示名只作展示，canonical repository 与 ID 承担校验。
- 新 `start-plans` 在事务内确认目标映射仍启用且该项目的 repository 与已准备值相同；改变另一个项目的配置不使本项目材料失效。目标路径或资格改变时返回 `conflict`，要求重新准备，不悄悄替换 manifest。
- 排队 payload 固化 `project_snapshot`（从已登记 manifest 的上述四字段复制），并保持 `planner_input_sha256` 绑定。之后 runner、发布、派发及其 runtime grant/worktree 均使用该请求/任务的快照，不查当前设置来覆盖路径。
- 保存映射不更新 `tasks/requests/planner_inputs`，不取消请求、不重发、不解除 hold。已排队/执行轮次可继续原仓库；界面保存前明确说明这一点。停用项称“停用新规划”，不能让用户误以为已暂停在执行任务。
- 已存在但可重新规划的任务，用户重新准备并明确提交新规划时才采用当前映射；`start-plans/_submit_one` 的状态、活动请求、发送不明、材料、方式、插件/运行端及配置校验全部通过，确定创建新请求或为未授权旧请求登记新输入时，才同事务更新任务三项登记字段。已授权请求的 deduplicated 返回不更新任务或旧快照；任何失败沿现有 `error → _SubmissionRejected` 回滚，须断言失败时任务字段、状态和事件均未改变。第三步如发现新旧路径不同，显示旧路径 → 新路径；用户确认排队即确认该次变更。旧计划文件与历史不改。
- 已有旧请求无新字段时，以其已登记 manifest 或 `tasks` 三项字段构成可信旧快照；不按当前名称去猜仓库。无法取得可信身份时拦截并说明，不信任模型 frontmatter 自报。
- `planfile.check_plan_meta` 增加 `expected_project` 参数；产品发布/派发/Plus 预校验调用都传可信快照，比较 ID、登记显示名快照与 repository。原模型快照、source/requirements/plan hash、远端 task.projectId、执行确认与发送不明闸门全部保留。缺参数的旧版纯函数兼容只允许旧常量的严格配对，不能成为新动态项目的逃生入口。
- `planner_runner.build_plan_meta` 优先且统一取请求固化身份，不再对新请求按名称回落项目 ID。新计划写入 `<plan_root>/projects/<project_id>/...md`；对 ID 做 ASCII 字母数字/下划线/连字符的有界验证并验证路径位于 Plan 根内。显示名即使包含 `/` 也不作目录片段；旧 Plan 路径保持可读，不移动历史文件。
- `sync-tasks`、Review-fix、recheck 等既有登记/校验消费者沿原任务快照；只替换实际仍依赖名称/常量的分支，不重构远端状态机。旧任务读回及当前登记计划的安全派发不因配置解除而失去历史身份依据。

### 4. 修复本次实测的路径隔离缺口

**待处理与设置**：待处理仍保留请求详情，任务级动作导航到共用任务详情，调整顺序/释放失联等请求级动作在请求详情完成；两类对象不混淆。最近失败历史默认折叠，不把已恢复的旧失败当成当前需人工。设置增加“项目与仓库”分组，其他角色分组保留；仅加载当前分组需要的配置/能力，切换不覆盖未保存草稿。通用的自动化区分“允许自动领取新请求”（core paused）与“本机定时运行执行端”（scheduler preference），说明已开始任务继续运行、关闭定时不禁止用户手动运行；不改变这些控制的实际语义。技术诊断成功项和只读路径折叠，失败项持续可见；调度状态/立即运行可达且保留执行端与任务执行的区别。

**异步与可访问性**：映射获取/保存、To Do 刷新、详情任务切换使用请求 generation/项目 ID 归属守卫；晚返回旧响应不得覆盖当前页面、草稿或选择。重复保存/开始在在途时禁用，超时展示当前命令错误，不自动再提交。配置浮层不卸载 PlanningView，保留其本地材料状态；返回后仅清除确实已失效的选中项并说明原因。加载失败保留已有内容但标出未更新，不冒充空列表。Tab/Enter/Escape、详情左右切页、VoiceOver 文本和完整长标题/路径可复制均需保留；破坏性动作无默认 Enter 捷径。

7. `KANPILOT_APP_SUPPORT` 隔离默认 runs，DB 显式 runs 根仍优先；两项 fake runner 用例在临时根通过，所有产物可追溯到 fixture，不能靠放开正式目录权限通过。
8. Swift 新响应与旧 To Do 响应缺新增可选字段都可解码；网络/目录/保存错误不会解码为空列表，晚响应不覆盖新选中/草稿。

### T1/T2 原生用户流程

构建独立测试产物，不覆盖 `/Applications` 或现有 `dist/KaneoPilot.app`：

```sh
mkdir -p build
project_ui_output="$(mktemp -d "$PWD/build/project-ui-check.XXXXXX")"
APP_OUTPUT_DIR="$project_ui_output" scripts/build_app.sh
```

构建由主控串行执行，现有脚本的 DerivedData 是共享路径，不与其他构建同时写入。主控为**此临时产物**用 macOS 自带 `PlistBuddy` 设置独立测试 Bundle ID，例如 `local.kaneopilot.project-ui-check.<本次标识>`，重新执行脚本已有的 ad-hoc codesign/verify；正式应用的身份与文件保持不变。这样 UI 的 AppStorage/UserDefaults 操作写入独立测试域，不能只用同 Bundle ID 副本加临时 DB 来冒充偏好隔离。

启动前：核对包内核心 hash 与源码；用临时 `KANPILOT_APP_SUPPORT/KANPILOT_DB/KANPILOT_PLAN_ROOT/KANPILOT_REPOS_ROOT`、独立 `KANPILOT_FAKE_STATE`，真实核心模式的 `KANEO_CREDENTIALS_PATH` 也仅指假远端凭据。仅对上述唯一测试 Bundle ID 用标准 `defaults write <测试BundleID> executorSchedulingEnabled -bool false` 预设关闭定时调度，不改正式偏好；隔离 MCP 偏好默认关闭。通过进程继承 env 直接启动这个候选 App，不能复用已经运行的正式 App。只使用 FakeCore/隔离核心及 stub 后端，先确认没有生产调用能力；本轮不实际启动它。

主 agent 在 macOS 14+ 本机原生界面核查，窗口 **1180×760 / 900×600 / 1440×900**，浅/深色各覆盖关键页面；记录构建、数据源、窗口与操作结果，旧系统未实测就注明。

1. 从设置新增 StarTool 映射；从规划阻塞行打开同一页、保存并返回，已选任务/补充/文件不丢，项目变为可准备。失败、离线与重复保存均可解释并恢复。
2. 从看板待办进入计划；从待处理、运行记录、归档/回收站进入同一五段详情，起始 tab/返回路径正确；标题只显示一次，概览无需翻多屏技术字段即可知道下一步。
3. 真正读取核验计划后才可确认执行；哈希变化/未核验时禁用且说明原因。发送不明的原证据与裁决始终可达，失联释放/重试/归档/永久移除保留原前置和确认。
4. 三步规划通过选取、材料问题、补充/排除、确认排队、部分失败/幂等结果走通；逐任务覆盖仍可选择且最终摘要正确；已排队与已领取/运行文字严格区分。
5. 900×600 列表免横滚，可看到主动作；模式切换、筛选、批量选中不丢状态；看板六列不丢卡、不重归类。长项目名、40+字标题、中文空格路径和至少30张任务无重叠，完整内容可查看复制。
6. 设置切组不触发所有后端无关检查、不覆盖未保存草稿；失败不因折叠消失。全局暂停、任务暂停恢复、定时调度关闭与手动运行含义可区分，实际语义不改变。
7. 键盘/VoiceOver 走完选择项目、目录选择、保存、三步返回、五段切换与更多操作；没有默认触发危险动作。无需新增截图回归平台，保留代表性对照截图/操作证据即可。

### 与真实服务的边界、交付

用 FakeKaneo 证明身份/路径与生命周期规则，用原生候选 App 证明交互；两者不冒充正式 StarTool 已接入。未来实施时，如会话授权和联网权限允许，可以用正式环境仅 GET 项目列表核对 StarTool 的真实 ID、项目名，且只读检查用户实际选择的目录。写正式映射应由用户实际配置或另有明确授权，不把实施本地代码等同于已授权改正式配置/任务。

本任务不以发送付费 prompt、真实 Kaneo 状态推进、替换正式 App 或发布 DMG 为验收必需；这些另循已有授权。真实服务无法读取时标明相关项未验证，不伪造 ID/路径，也不阻止已完成的隔离与 UI 工作交付。

收尾仅处理本任务创建的临时进程/夹具与独立构建产物，不清理用户 dirty tree、正式运行记录或其他工作树，不自动提交/推送。按 T1/T2 报告“实现内容 / 本次自动检查 / 原生体验 / 真实服务读取 / 剩余项”；必要验证未完成为“实现中”，适用检查完成后为“待体验”，只有用户明确确认才记“已验收”。

## 风险与规避

| 具体风险 | 对应处理 |
| --- | --- |
| 有页面但核心仍残留名称白名单 | A 核对全部实际消费者，贯通 fake publish/dispatch guard；主控核对正式打包 hash |
| 修改仓库后旧请求被偷偷换路或全部失效 | 决策 3 的登记快照与明确重新规划语义；保留旧字段兼容及 targeted conflict |
| 清空映射又被旧种子复活 | 首次持久化完整集合，解除保留未配置项，保存集合存在后不再回落种子 |
| UI 精简掩盖安全动作或绕过计划核验 | shared allowed_actions、verified hash 与独立裁决区，逐项真实操作核验 |
| 旧计划仍在施工时共同编辑 BoardView/TaskDetailTabs | 实施前确认所有者；同一文件移交后串行，主控唯一负责本计划的详情整合；不改旧验收目标 |
| 测试或演示 App 写正式数据/启动真实调度 | 先修运行记录根隔离，确认所有根/后端为临时与 stub，候选进程关闭定时调度，不通过提权访问正式目录解决 |
| 源码推断与当前安装 UI 不一致 | 本轮已明确原生访问受限；施工前用候选/同版本窗口建立对照，保持本计划用户效果，具体组件偏差由主控修正规格 |

执行者可以自行决定局部命名/函数组织，不能改本文件的身份、数据影响、视觉层级、授权或验收目标。同一阻塞两次有不同依据的尝试仍不解决时，记录预期/实际/证据，暂停依赖部分并继续独立工作；有新证据再继续，不能盲目重试或隐瞒未验证项。

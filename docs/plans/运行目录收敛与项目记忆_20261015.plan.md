# 运行目录收敛与项目记忆绑定

## 概要

用户提出两个问题：

1. 规划与评审会为每轮或每个 commit 新建独立工作树目录。批量自动化后目录持续增长。
2. 独立目录读不到 Plus 的项目级记忆。

两者根因不同，分开处理：

- **目录增长**：路径按 run 或 commit 生成，核心中没有任何回收路径。主修复是稳定的槽位池（阻止增长），辅以历史回收（清理存量）。
- **记忆**：Plus 把项目级记忆绑定到真实路径或分组。独立目录是未分组路径，读取的是一个从未写入的键。全局指令 `~/.pi/agent/AGENTS.md` 与路径无关，文件存在时独立目录本来就能读到它，因此问题 2 只针对项目级记忆。
- **记忆的损失无法从数据确认**：探针前，Plus 库中不存在 `projectMemory`、`projectGroupMemory`、`projectGroupInstructions` 三类记忆 namespace，全局指令文件 `~/.pi/agent/AGENTS.md` 也不存在。以 `agents.md`、`instruction` 为关键词的扫描命中 15 行：`context-insights-v1` 的 9 行无“记忆”或“memory”字样，`team-*` 的 6 行未逐行核对（见「现状 4」）。探针后，已分组的 HOI4 在 `projectGroupMemory`、`projectGroupInstructions` 中各有 1 行（内容为空）；0.5 后残留的 0 字节全局指令文件已删除。已定位与未定位的部分见「现状 4」与「探针结论」。

推荐顺序：Phase 0（定位记忆）→ Phase S（规格先行）→ Phase A（存量回收）→ Phase B（槽位池）→ Phase M（记忆绑定，按 D5 选择，推荐 M4）。

历史状态（2026-10-15 编制时）：仅计划，未实施。2026-10-16 用户明确要求开始执行；本轮状态为实现中，实施记录见文末。原规划阶段未改代码、未写库、未构建、未安装、未提交、未切换分支。依据为 2026-10-15 的只读核查（磁盘计数与大小、库只读计数、代码锚点；§5 于 2026-10-16 复核修订）与 Phase 0 探针（HOI4，0.0–0.5 已执行，结论见「现状 4」下的「探针结论」；0.7 未执行）。文中数字是核查时点的快照，执行前需复测。

## 不做的事

- 不让规划或评审在真实仓库路径中执行（§5.24.3-1；`pi_desktop_planner.py:1013-1014` 注释）。
- KaneoPilot 不写 Plus 的 SQLite，也不调用 `projects.remove`（它会批量删除会话，见「现状 3」）。
- 不池化执行用的 `<task>/branch` 工作树。它是任务分支的持久工作区，回收条件由 AGENTS.md 的分支清理规则约束。
- 不使用 `worktree remove --force`、`clean -x`、`reset --hard`。重置与删除只在守卫通过后执行。
- 验证时不对 live 库运行 `prepare-plan-input`、`start-plans` 或其它会创建请求与目录的命令。测试一律使用 `KANPILOT_DB` 指向的隔离库。
- 不改动主工作区的 11 个已修改测试文件（含 `tests/test_save_state.py`），也不改动另外 3 个未跟踪计划。

## 关键设计决策

### D1 槽位池（推荐）

- 池的范围：每个真实仓库最多 N 个规划/评审槽位，默认 N=4，可配置（配置入口待定）。"仓库"以 `git rev-parse --git-common-dir` 的绝对路径为准，使同一仓库的多个工作树共享一个池。
- 路径：`<worktrees_root>/pool/<repo_key>/slot-<k>`（`worktrees_root` 见附录 A），`repo_key` 为仓库标识的短哈希。
- 懒创建：槽位按需创建，任一时刻同一仓库的槽位数不超过 N，不预先建满。
- 槽位是 detached worktree（`git worktree add --detach`），只创建一次，之后复用，不建分支。
- 规划与评审通过租约（D2）获得槽位。执行仍使用 `<task>/branch`。
- 不纳入池：`<task>/branch` 及其恢复路径（`review_resolution.py:255-281`）。
- 执行回退（`cmd_dispatch` 的 `<task>/<run_id>`）是否纳入池，取决于触发频率（未计数，未验证项 5）。在核实前，它只纳入 Phase A 的回收范围。
- 侧边栏（推断，见未验证项 10）：槽位会话若经 `ensure_project` 建行，每个槽位至多一行（按路径去重），每仓库上限为 N 行。是否在侧边栏隐藏属于 PI-Desktop 侧，另起计划。
- 空闲仓库的整池回收：某仓库的池在没有活动租约、且没有非终态请求或活动轮次引用，超过保留期后，可整体回收（经 D4 的确认与回执）。这使目录数的上限随"活跃仓库数 × N"有界，而不随时间增长。

### D2 租约、检出与隔离

- 新表 `worktree_slots`（schema 5→6，B1）：`slot_id`、`repo_key`、`path`（唯一）、`state`（`free` / `leased` / `quarantined`）、`holder_stage`、`holder_id`、`sha`（目标检出的提交）、`lease_expires_at`、`heartbeat_at`、`updated_at`。
- 获取：在 `BEGIN IMMEDIATE` 事务内选取一个 `free` 槽位，写入持有者、目标 sha 与到期时间；事务外完成检出（见下），失败则置 `quarantined`。若该仓库的槽位数尚未达到 N，先写回执再创建新槽位。没有可用槽位时返回排队状态，不超过 N。
- 产物先于释放：规划与评审的产物（`.kaneopilot-plan-material/`、`.pi/plan/*.md` 等）必须在释放前读取或拷贝到既有存储（`planner_inputs` 或 executor-sessions），释放删除之后槽位才可再次使用（B7）。
- 释放：
  1. 只删除本系统已知会写入的产物路径（与 `_snapshot_has_disallowed_changes` 的允许清单一致：`.kaneopilot-plan-material/`、`.pi/plan/*.md`）。
  2. 再执行 `git status --porcelain`。为空则置 `free`。不为空则置 `quarantined`，不做任何清理。
- 检出（获取时，守卫通过后）：`git checkout --detach <sha>`。不使用 `--force`、`reset --hard` 或 `clean`；释放步骤已确认工作区干净，故无需清理未跟踪文件。被忽略的缓存保留（不加 `-x`）。
- 守卫：检出前若 `git status --porcelain` 非空，置 `quarantined`。不丢弃不属于本系统的改动。
- 租约过期：只有心跳超时的 `leased` 才进入释放流程，并经过同一守卫。过期阈值必须大于该阶段的最长运行时间，且释放前须确认持有进程已结束（B2 中定义）。否则会在运行中的会话下删除产物。
- 失败：检出、守卫或释放失败置 `quarantined`，写入 attention-list。解除隔离只能经核心命令，且需用户确认。
- 所有创建、检出、删除工作树的 git 操作，先写 `runtime_operations` 回执（AGENTS.md 外部副作用规则）。现有 `prepare_*` 是否写回执待核实。

## 验收标准

A. 目录增长：连续 20 轮规划与评审后，每个仓库的 `worktrees/pool/<repo_key>/` 下目录数 ≤ N。这些轮次不新增池化范围内的 UUID、`review-*`、`plan-*` 目录。
B. 并发：2 个规划与 1 个评审同时租约，槽位不重复持有，仓库槽位数不超过 N，释放后状态正确。
C. 安全：槽位内放入未知改动后释放，槽位不被重置，进入 `quarantined`，attention-list 可见。
D. 评审一致性：评审槽位 HEAD 等于快照 sha；分支后续移动不影响评审内容；`verify_root` 通过；`Path(snapshot) != review_root` 检查仍成立。
E. 回收：dry-run 候选与实际删除一致；每个删除有回执；有活动引用的目录不被删除；删除后 `git worktree list` 与磁盘一致；执行类目录在 A0 通过前不在候选中。
F. 记忆：Phase 0 结论有前后对比为据。M4 下：槽位会话的启动上下文与每轮刷新都解析到真实项目的记忆（同一探针前后对比）；伪造、过期、指向其他仓库的登记项被拒绝；plan/goal 模式写入仍被阻断。M1 下：分组会话的启动上下文包含分组记忆。
G. 测试：`cd core && python3 -m pytest tests -q`、`python3 -m pytest tests -q`、`python3 -m pytest tests/rehearsal -q` 通过。测试不包含 live 模型调用，使用隔离库。
H. 分支清理：relay 与 topup 合并后，来源分支（本地；若合并前已推送则含远端）已删除，临时工作树已清理，`git branch -a` 与 `git worktree list` 的核对结果已报告。

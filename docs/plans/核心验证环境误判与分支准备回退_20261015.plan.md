# 核心验证环境误判与分支准备回退

## 概要

执行轮已经结束、本该进入评审的任务，被打回到"重新准备分支"。StarTool 任务 `kkw1goas3mo7sse8orfo1ibd` 的执行轮 `8fa879be` 于 2026-10-14T18:30:07Z 正常结束（exit 0）。2026-10-15 装入监控补给修复后，核心验证跑了 4 条 Gradle 命令，全部因 JDK 版本不符退出 1。核心把它当成"验证未通过"，引擎随即自动开了修复轮（重新规划，1/2）。补建分支时先撞上 10-13 遗留的空分支（`branch_exists`）；用户把 PR 目标分支改成 main 后，又因 origin 上没有 main 受阻（`delivery_base_unknown`），界面显示「无法确定交付目标分支：Git 操作失败：fatal: Needed a single revision」。

根因：

1. 核心验证只把 rc=127 / "command not found" 认作环境失败。Gradle 在 Java 8 上报 "This build uses a Java 8 JVM" 并退出 1，被判成质量失败，进入自动补救。
2. 自动补救默认"同分支修复"，但这一轮跑在独立工作树（detached HEAD）上。重新规划会从目标分支新建分支工作树，本轮改动带不过去——这就是"回到最开始"。
3. 补建分支撞上遗留空分支，失败路径又把 `delivery.mode` 从 manual 改成 pr；PR 目标分支保存时不校验 origin 上是否存在。
4. 自动补救一旦开出就无法撤回，没有任何动作能回到原轮次重新验证。

本计划：

- 核心验证增加环境签名识别（JDK 版本、Android SDK、已连接设备），命中即 `verification_environment_failure`：原轮次原地重验，不重新规划，不消耗补救轮。「重新运行验证检查」同样注入项目 verify_env；人工接管任务也能「重新验证本轮」。
- 同分支修复增加前提：本轮必须在已登记的任务分支工作树上。不满足时，引擎补救和评审修复都转待处理 `fix_branch_unavailable`（「本轮改动在独立工作树，无法同分支修复」），保留本轮成果，由用户决定。
- 补建分支时，核对为空的遗留任务分支直接收养；否则 `branch_exists` 写明具体原因。失败路径不再改动 delivery 模式。
- 新增「撤回自动补救」（`revert_engine_fix`）：把任务带回原轮次的验证待处理，并退还补救计数。自动补救开始前记录任务快照，供撤回还原。
- PR 目标分支保存时校验 origin 上存在；项目页显示真实默认分支；`branch_exists` 与 `delivery_base_unknown` 文案分开；git 原始报错转成可读说明。
- 规格先行：protocol、automation-contract、state-model、ui-spec。

状态：实现中；参数于 2026-10-15 确认，2026-10-16 用户确认继续执行剩余收尾计划。

**根因**

1. **环境失败只认 rc=127。**
   - `verdict._command_not_found`（`verdict.py:138`）只看 `code == 127` 或输出含 "command not found"。`evaluate`（`:210`）据此算 `environment_failure`（`:224`），shadow 分支（`:349`）同一口径。
   - Gradle 的 JDK 不符、SDK 缺失、没有设备都是 exit 1，落进 `verify_failed`。`auto_monitor.py:137` 于是给出 `verification_unconfirmed`，进入阶梯 3 自动补救。
   - 规格（protocol §5.18.6 `:743`）只写了 rc=127，没有其他环境类口径。
2. **「重新运行验证检查」不用 verify_env。**
   - `verification_checks._path_environment`（`:147`，调用点 `:363`）从 `os.environ` 起步，只加本轮执行的 PATH 前缀；`verification_process.py:70` 用 `/bin/bash --noprofile --norc -c`。项目 verify_env 完全不参与。
   - 所以即使用户补齐 verify_env，这个动作也会继续失败：核心验证（login shell + verify_env）与用户检查的环境不一致。
3. **独立工作树的轮次被"同分支修复"。**
   - §5.27.12（`:1505`）规定 verify 失败沿 `resolve replan` 同分支修复。引擎 `_quality_retry`（`loop.py:270`）和 `_engine_fix_guard`（`cmd_queue.py:463`）只核对绑定是否未变，不看本轮在哪个工作树；`steps.py:48` 对 verify_failed 一律下 `replan`。
   - `replan`（`cmd_queue.py:843`）只把任务转回 needs_plan + plan_wanted。intake `_submit`（`auto_intake.py:93`）看到没有 `delivery.branch`，就从目标分支新建分支工作树（`git_delivery.prepare_branch_worktree`，`:200`）。本轮 detached 工作树里的改动不会进入新分支，新规划也从干净的基线开始。
   - 评审 `changes_requested` 走 `core.start_fix_round_inline`（`cmd_exec.py:1095`，`core.py:421`），同样转 needs_plan + plan_wanted，问题相同。
   - 只有 `delivery.mode=pr`（或 `workspace_version=1`）的任务，执行轮才跑在任务分支工作树上（`core.requires_branch_review`，`core.py:318`；`verdict.binding`，`verdict.py:245`）。被接管后又恢复自动处理的任务，delivery 保持 manual，正好落进这个缺口。
4. **遗留空分支阻塞补建，失败路径改写 delivery。**
   - 重新关联（`cmd_archive.py:160`）把 delivery 整体替换为 manual，但不处理磁盘上的任务分支和工作树。
   - `prepare_branch_worktree` 发现本地或 origin 上已有同名分支就报 `branch_exists`（`:215`），不区分"空的遗留分支"和"有内容的分支"。
   - 失败时 `_submit` 把现有 delivery 传给 `_failure`（`auto_intake.py:134`），`_adopt` 无条件写入 `dict(delivery, mode="pr")`（`:59`）。manual 变成了没有分支字段的 `{"mode":"pr"}`，正是 `_release_manual_takeover` 刻意避免的"PR 模式但不可发布"半态；`requires_branch_review` 也随之变真，原轮次的 detached 绑定再也对不上。
5. **PR 目标分支保存时不校验。**
   - `validate_automation`（`automation_policy.py:72`）只做格式校验，`cmd_set_project_automation`（`:151`）直接落库。
   - 要到 intake 的 `resolve_base`（`git_delivery.py:182`）才失败，报的是 git 原文；项目页占位符固定写"例如 main"（`ProjectMappingsView.swift:440`），不显示真实默认分支。
   - `branch_exists` 与 `delivery_base_unknown` 共用标题「分支准备受阻」和同一句说明（`Components.swift:729`、`:745`），用户无从区分。
6. **自动补救开出后无法撤回。**
   - `replan` 清空了 `sent/send_state/sent_at/lock_retained`，补救计数也已记下（`_record_engine_fix`，`cmd_queue.py:531`）。
   - 现有动作里，`replan` 只会继续往前；`reverify`（`verification_recovery.candidate`，`:13`、`:18`）只认 stage 为 monitor 的 `verification_unconfirmed`。没有动作能回到原轮次的验证。
   - 补救开始时也没有记录"补救前"的任务状态，撤回时无从还原。

## 关键设计决策

**D1 环境签名分类（`verdict.py`）。**
- 用 `_environment_reason(code, tail, launch_failed) -> Optional[str]` 取代 `_command_not_found`（`:138`），只在退出码非 0 或启动失败时判定。返回值：
  - `command_not_found`：rc=127、"command not found"、启动失败（沿用现有口径）；
  - `jdk_version`：`This build uses a Java \d+ JVM`、`requires at least JVM runtime version`、`Unsupported class file major version`；
  - `android_sdk_missing`：`SDK location not found`；
  - `no_connected_device`：`No connected devices`。
- 新检查在内存中的原始输出尾部逐行匹配，只持久化受控原因枚举与脱敏输出；历史收据缺少有效枚举时从已脱敏尾部回退重判。模式表集中定义，单测逐条覆盖。成功与超时优先排除环境类。此时机在复审中修正，避免单字符敏感值脱敏破坏 SDK/JDK/设备签名；原文仍不落盘，D1 的用户行为不变。
- 每条检查增加 `environment_reason`。`command_not_found` 字段保留，含义不变（只表示 `command_not_found` 这一类），兼容既有消费方。
- `evaluate`（`:210`）：`env_failure = any(c.get("environment_reason") for c in checks)`（`:224`）；结果增加 `environment_reasons`（去重、保序）。detail（`:231`）按原因给出处理提示：
  - command_not_found：沿用「验证命令不存在（环境类，阶梯 2），请修复 verify 环境后重试」；
  - jdk_version：「验证所需 JDK 版本不符（环境类）：请在项目映射的 verify_env 设置 JAVA_HOME 后重新验证本轮」；
  - android_sdk_missing：「未找到 Android SDK（环境类）：请在 verify_env 设置 ANDROID_HOME 后重新验证本轮」；
  - no_connected_device：「没有已连接的设备（环境类）：请连接设备后重新验证本轮」。
- shadow 分支（`:349`）用同一分类器。`auto_monitor.py:137` 本来就按 `environment_failure` 映射 failure_code，不用改。
- 同一组检查只要有一条命中，整组按环境类处理，与现有 rc=127 口径一致。理由：误判成环境类，代价是等用户点「重新验证本轮」；误判成质量类，会自动重规划，丢掉独立工作树的成果（本次事故）。
- JDK 签名有本次收据为证。SDK 与设备两类签名目前只是候选：实现时须在临时克隆里实际复现并采集夹具，按实测输出定稿，不得在任何执行轮工作树里跑。

**D2 「重新运行验证检查」注入 verify_env。**
- `_path_environment(events)`（`verification_checks.py:147`）改为 `_verification_environment(conn, task, events)`：
  - 仍从 `os.environ` 起步，加本轮执行的 PATH 前缀；
  - 再叠加项目 verify_env，与核心验证同源读取（`project_mappings.items[project_id].verify_env`）；verify_env 里有 PATH 时以它为准。
- 回执只记录 verify_env 的键名列表和整体 sha256，不记录值。
- shell 不改，仍是 `/bin/bash --noprofile --norc`（`verification_process.py:70`）。这个动作沿用执行端 PATH 复核；叠加 verify_env 后，显式环境与核心验证一致。
- 不放宽 `verification_recovery.candidate`（`:13`、`:18`）。

**D3 人工接管任务也能「重新验证本轮」。**
- 现状：`verification_environment_failure` 的 resume 只对托管任务开放（`derive.py:581`；`cmd_queue.py:731` 对非托管任务直接 conflict「该任务不受自动化管理」）。D1 让更多失败归入环境类，人工接管任务若因此没有恢复动作，就会卡死。
- `derive.py:581`：`verification_environment_failure` 且 `failure_stage=monitor` 时，不论是否托管都加 `resume`。
- `cmd_queue.py` resume 分支（`:729` 起）：在"不受自动化管理"检查之前单独处理这个原因，目标与托管任务相同（running + monitor，原 run/plan/工作树）。非托管任务不写段字段（`update_automation` 本来就只对托管任务执行）。

**D4 同分支修复的前提：`fix_branch_unavailable`。**
- 新增 `core.same_branch_fix_ready(task, binding=None) -> (bool, reason)`，紧挨 `requires_branch_review`（`core.py:318`）：
  - `requires_branch_review(task)` 为假 → `(False, "detached")`；
  - delivery 缺 `branch` 或 `worktree_path` → `(False, "no_branch_worktree")`；
  - 传入 binding 时，要求 `binding.branch == delivery.branch` 且 `binding.worktree_path == delivery.worktree_path`，否则 `(False, "worktree_mismatch")`；
  - 其余 `(True, None)`。
- 引擎补救（只针对 verify_failed；empty_diff 走同计划重跑，没有改动可丢，不受影响）：
  - `_quality_retry`（`loop.py:270`）：`reason == "verify_failed"` 且判定为假 → `block = "fix_branch_unavailable"`，沿现有 BLOCK 路径下发。`steps.py:48` 对带 block 的补救下 `resume`，不会 replan。
  - `_engine_fix_guard`（`cmd_queue.py:463`）权威复核：用收据 binding 再判一次，为假则 `block = "fix_branch_unavailable"`，放在预算与上限判断（`:501–507`）之前，不消耗补救轮。block 不追加补救行（现有语义）。

**D5 收养遗留空分支（`git_delivery.prepare_branch_worktree`）。**
- 位置：`fetch --prune`（`:203`）和 `resolve_base` 之后、分支与路径的 `branch_exists` 判定（`:210–217`）之前。
- 本地 `refs/heads/<branch>` 存在时，以下全部满足才收养：
  1. origin 上没有同名分支（fetch --prune 之后 `refs/remotes/origin/<branch>` 不存在）；
  2. `git worktree list --porcelain` 中，预期路径 `<worktrees>/<task>/branch` 登记在该分支上，且目录存在；
  3. `git rev-list --count <base_sha>..<branch>` 为 0，即相对目标分支没有自有提交；
  4. 该工作树 `git status --porcelain --untracked-files=all` 为空（从严：构建产物也算不干净）。
- 收养：在该工作树执行 `git merge --ff-only <base_sha>`，返回与新建相同形状的 delivery（`branch`、`worktree_path`、`base_branch`、`base_sha`、`head_sha`），另带 `adopted: true`。
- 调用方把 `adopted` 带进 start-plans 的 automation 载荷。核心写 delivery 的同一事务里记事件 `branch_worktree_adopted`（branch、worktree_path、base_sha）；`adopted` 键不落进 delivery。
- 任一条不满足 → 仍报 `branch_exists`，说明写具体原因：
  - 「本任务分支已推送到 origin，未自动收养」；
  - 「本任务分支有 N 个目标分支之外的提交，未自动收养」；
  - 「本任务分支的工作树有未提交改动，未自动收养」；
  - 「本任务分支没有在预期路径登记工作树，未自动收养」；
  - 「本任务分支的工作树目录缺失，未自动收养」。
- 本地没有、只有 origin 上有同名分支时，沿用现有 `branch_exists`。

**D6 撤回自动补救（`revert_engine_fix`，「撤回自动补救」）。**

  - 补救之后没有新规划：`plan_generated_at ≤ row.at`；`row.at` 之后既没有 plan 请求，也没有新的 planner 输入。
  - 没有活动请求；`run_id` 仍是任务的当前执行轮（与 `verification_recovery.candidate` 同口径）。

## 风险

- **签名误判。** 签名表只收录"环境缺失"的明确措辞，并要求退出码非 0。SDK 与设备签名必须按实测夹具定稿。
- **整组判定。** 只要一条命中签名，整组就按环境类处理，可能盖住同组里真正的测试失败；重验时会重新暴露，代价可以接受。
- **jenv。** 本机 jenv shim 不可用，login shell 的 `java` 落到 Java 8。在 verify_env 里显式设置 JAVA_HOME 只修复 KaneoPilot 的验证；其他依赖 jenv 的工具不在本计划内。
- **attention 排序。** 两个原因落 `needs_user_other`（阶梯 4），排序会靠前，与 ladder 的环境阶梯口径不完全一致，属既有行为。
- **PR 目标分支校验不阻塞 preflight。** 网络不可用时保存会返回 `unverified`，问题留到 intake 暴露（届时说明已经可读）。
- **收养从严。** 工作树里有构建产物也会拒绝收养，需要用户手动清理后重新准备分支。
- **撤回的时间窗。** 只在分支准备受阻、尚未发出新规划时可用。新规划一旦提交，只能走 replan、dismiss 等既有路径。
- **存量行没有快照。** 本任务这一行没有 `before`，按 D6 的兜底还原（`sent_at` 取 dispatch_sent 事件，delivery 回到 manual）。如果本轮工作树被改动过，binding 重算不等，撤回会被拒绝。
- **legacy 项目的评审修复。** `same_branch_fix_ready` 也作用于 legacy 的评审修复路径。legacy 任务通常是 pr 交付且有分支，行为不变；delivery 为 manual 的任务会从"静默丢弃改动"变成"转待处理"。

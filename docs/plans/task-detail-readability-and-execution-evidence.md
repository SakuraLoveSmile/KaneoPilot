## 冻结的修复结果

1. **执行阅读 T1**：保留当前 2 秒增量刷新、逐条展开/复制、搜索、上滚停止跟随与回到底部语义。无新消息且状态未变时不发布新消息数组或安排自动滚动；有新消息/修订时仅处理改变的行，仍按 `seq` 排序，展开状态跟随消息 ID。折叠的长正文只排版可见预览，完整原文仍可复制，搜索命中时仍能看见命中内容。先在同一合成长会话和窗口条件下测主线程耗时与卡顿，再修已证实热点；不新增通用缓存系统或改变核心游标协议。
2. **计划阅读 T2**：继续使用 `get-plan` 的核验结果，默认“渲染”、可切“原文”；原文逐字可选中复制。渲染采用 Foundation `.full` Markdown 的 `PresentationIntent`/`NSPresentationIntent` 语义结构，桥接只读、可选中的 AppKit `NSTextView`；先实测系统默认块排版，不足时按 intent 显式设置原生段落、列表、代码、表格样式，不手写正则 Markdown 解析器。标题 H1 用现有 18pt、其余标题/正文以 13pt 字重和间距区分，代码沿现有 12pt 等宽，颜色/分隔沿系统 token。列表缩进、引用、水平线、GFM 表格与长代码都应可读；超宽单元格/代码行可以换行或在内容区水平查看，文字可完整选择复制，不能撑宽整个 sheet。链接仅由用户点击时以 `http/https` 交系统打开；HTML 不执行，图片只显示 alt/占位，不自动读取远端媒体。跨块选择复制须保留合理换行及列表/表格内容。核验失败仍不展示旧正文、不允许“确认并安排执行”。
3. **计划头部 T2**：标题单独占满第一行且最多两行；状态、类型、时间、哈希和可截断路径放在元数据区，长路径中间截断但能复制/在 Finder 显示。模式分段与“打开计划文件”“在 Finder 显示”置于独立操作行，宽度不足时在该行换行，不与元数据争宽；右上无裁切、重叠或漂浮残字。保留既有底部确认条与按钮可用性规则。
4. **评审 T3、记录 T4**：五段导航始终固定在浮层顶部，切页不改变浮层的有效尺寸。评审无数据时空态只在导航以下的内容区居中，保留当前图标、标题和说明；有数据时保留结论、报告、修复任务等原字段与“打开报告”。记录页为“尝试记录”“事件时间线”两个不嵌套卡片的区段，单个外层滚动；尝试行按时间/阶段/结果/说明四列自然撑高（结果图标+文字），事件行按时间/类型/摘要三列，行高不低于 40pt，固定列不折断 `round_observe` 等类型。默认显示 `EventItem.summary`，点击一行可展开完整 note/evidence 或结构化 detail 并复制原文；不再用两行裁切作为唯一阅读方式。未知 kind 保留原值且可完整查看。数据源继续是 `get-task.attempts` 与 `list-events(task_id, limit:200)`；此页只称“最近记录”，不冒充全史。
5. **Goal 报告完成判定 T5**：`pi` 后端保留 `docs/protocol.md` §5.18.4 原三证据口径；**此规则启用后所有仍要从 `running` 进入 Review 的 `pi_desktop` 轮次**，包括升级时尚在运行的旧轮次，都以 Canvas 背后的 Host 结构化报告为监控 AI 判断的主材料，而不是让模型从会话最后一句或退出码猜完成。新轮次派发 `spec.instruction` 明确本次真实 `cwd` 与原仓库只读边界；旧 spec/会话身份不改。`Bash` 工具名大小写归一、退出码保真仍须修，供报告证据与 Review 查阅，不再把“发现一条退出码 0 的命令”单独当 Plus 轮次的放行条件。

   **报告读取与身份。** Plus 本机 MCP 新增只读 `pi_goal_report_list {sessionId}` 和 `pi_goal_report_get {sessionId,executionId}`，由现有 Host `goalReports.list/get` 提供，不开放 submit/retry/finalize 写操作。Host 对 `ready` 文件重算 `file_hash/file_size`、核验 schema/身份后返回不超过现有 256 KiB 上限的完整报告与可信 `report_sha256`；超限、截断或 `pending/draft/failed/not_found/corrupt` 明确分态，不返回伪造正文。KaneoPilot 核对当前 `task_id/run_id`、`job.session_id`、`job.goal_approval.proposal_id`、已批准执行 turn 与报告 `sessionId/proposalId/executionId/turnId`；允许 `turnId` 沿本轮已记录的 `turn_adopted` 链核对，不能只凭同一 session 名称或标题匹配。KaneoPilot 发布计划的 `plan_sha256` 与 Plus Goal 契约的 `contractHash` 各管各的文件，不能直接比较成同一个哈希。无 `goal_approval`、报告跨轮/身份不符或 Plus 缺只读工具均不能放行。Plus 版本能力在 `exec-capabilities/dispatch-start` 发送前核验，旧 Plus 不静默走原消息猜测路径；PI CLI 不受影响。

   **AI 判断。** monitor AI 调核心只读 `get-goal-report {task_id,run_id}` 获取经身份/完整性校验的报告，再读取当前已批准 KaneoPilot 计划。它把报告作为**不可信数据**，逐项比对原计划验收、Plus 批准的 Goal 契约、报告的 criteria/steps/checks/evidences、limitations 与 nextSteps，输出结构化 `{decision:"complete"|"incomplete"|"uncertain",plan_sha256,report_id,report_sha256,criterion_reviews:[{id,result:"met"|"missing"|"failed"|"unknown",reason,evidence_refs}],reason}`。报告自称 `verdict=met` 是必要但非充分条件；`partial/blocked/unknown`、重要验收遗漏、明确失败或无法解释的证据缺口不可被 AI 升格为完成。AI 可引用报告中的实际检查/证据 ID 作理由；不机械要求每类任务都有测试命令，但计划明确要求的验证必须在报告中有可审查的结果或明确说明未能验证。只有 AI 判定 `complete`、列出的必需验收项均为 `met` 且全部必需验收项被说明，任务才能从 `running` 进入 `in_review`；最终 `done` 仍由独立 Review 通过决定。

   **核心硬闸与失败语义。** 这里区分 `execution_run_id=task.run_id`（被观察的派发轮次）与 monitor 请求自己的 `monitor_run_id`，两者不能互换。新核心命令 `record-goal-evaluation {task_id,execution_run_id,monitor_request_id,monitor_run_id,plan_sha256,report_id,report_sha256,decision,criterion_reviews,reason}` 先核对该 monitor 请求仍由 `kaneo-monitor` 领取且租约有效，再只读重新取回同一报告并核对当前任务/执行轮次/计划/报告 hash。登记 `decision=complete` 时，核心还须确定性核对报告 `status=ready`、`integrity.kind=structured`、`execution.status=completed`、`verdict=met`，审查项非空、ID 不重复、结果全为 `met`，引用的 criterion/check/evidence ID 确实存在于报告；不满足即拒绝记录完成判定。通过后把 AI 判定、理由、引用 ID 和两种轮次身份写入 `goal_report_evaluated` 事件。同一 `task_id/execution_run_id/plan_sha256/report_sha256` 已有判定时幂等返回原事件，不重复调用 AI；新的 monitor 请求可引用它，但必须自己仍是有效 claim。`advance-task in-progress -> in-review` 对 `pi_desktop` 必须带当前 monitor claim 与 evaluation event ID，核心在远端更新前**再次**复核当前任务的执行轮次、报告身份/hash、上述确定性报告底线、事件确由有效 monitor 请求登记、`decision=complete` 与执行终态 `completed + finished/0`；绕过 monitor 直接调用、旧判定或报告变化一律 `conflict`，不触碰远端。是否覆盖原计划全部验收要求由独立 monitor AI 作语义判断，核心只负责不可绕过的身份和报告底线。`pi` 后端维持旧接口。核心不把 AI 文案当身份凭据，也不解析 Canvas HTML/截图。

   **没有可用 Canvas 报告就没有完成。** `ready + integrity=structured` 才算可供 AI 分析的报告；Plus 自动生成的 `ready + fallback` 等同“没有完成报告”。执行中/报告仍在 `pending|draft` 时继续观察；执行终态落地后给 Host 最多 60 秒完成 outbox/报告发布，期间只读查询，不重发 prompt。过时仍无结构化报告、报告 `fallback`、AI 判定 `incomplete` 或明确 `partial/blocked` → `report needs_user`，`failure_code=execution_failed`，原因写明具体缺口，不自动重新派发。报告不可读/损坏或 AI `uncertain` → 不进入 Review，最多一次有界重读后同样交人工并保留区别于“已验证失败”的原因；临时读取失败不伪称没有报告。规则只作用于**后续推进动作**：已在 `in_review/done/needs_user` 的历史任务不回填、不降级或改判；升级时仍 `running` 的旧 Plus 轮次若无报告，按上述缺报告规则进入人工处理，不走旧消息三证据放行。截图中的轮次保持原 `needs_user`。
6. **派发名称 T6（仅新建的 `pi_desktop` 轮次）**：Plus 侧栏的工作区**主名称**使用已登记的 `task.project_name`（示例 `Music`），其稳定身份、实际执行 `projectPath/cwd` 仍是独立 worktree 的绝对路径；完整路径继续可在悬停/项目详情查看。同项目两个轮次可各有一个物理 worktree，主名称同为 `Music`，按路径分别归组，不按名称合并。会话主名称使用与 KaneoPilot 计划页一致的 `task.title`（示例“随机歌曲右侧按钮应随机新歌而非直接播放”），长标题在列表单行截断但完整标题可悬停/复制。`session_marker`、`task_id/run_id`、`session_id/turn_id`、计划哈希和事件关联仍是机器身份；显示名不得用于去重、路径生成、权限判断或完成判定。历史会话不批量改名。

   共享创建契约：KaneoPilot 在现有计划哈希/任务身份复核后，把 `workspace_display_name=task.project_name`、`session_display_name=task.title` 固化到**新轮次** `spec.json`；两者为展示快照，旧 spec 缺字段仍按旧语义读取/续接，不重新生成原 prompt。Plus 的 `pi_session_create`/Host `session.create` 增加可选 `projectName`，继续使用已有 `title`：`{projectPath:<真实worktree>,projectName:"Music",title:<计划页标题>,mode:"goal",...}`。Plus 复用已有 `projects.name` 并在同一次会话创建调用里保存名称，返回 `session:{id,title,projectPath,projectName}`；`SessionSummary.projectName` 为可选字段，旧客户端未传时保留 basename 默认。Plus 的工作区 `get/set` 对已有 path 从 `projects.name` 读回显示名，Sidebar 以 `projectMeta[path].name`（用户手工别名）优先，其次 Host `session.projectName`/工作区名称，最后目录 basename；工作区身份始终 keyed by canonical path。已有非 legacy 用户项目组或同一路径已有不同的自定义名称不得被 KaneoPilot 覆盖，返回明确 `CONFLICT`。名称包含空白控制字符或任务登记标题/项目名缺失时在创建会话前给确定性校验错误，不回退到 UUID；Plus 创建返回的两种显示名与请求不符时不下发 `agent_prompt`，保留已创建会话 ID 供人工检查，绝不自动再建一次。

   兼容门：Plus 的 `tools/list` 必须表明 `pi_session_create.inputSchema.properties.projectName` 可用；KaneoPilot `exec-capabilities` 和 `dispatch-start` 在任何 `session.create` 之前检查，旧 Plus 明确显示“版本缺少工作区命名能力”，不静默派发出 UUID 名称。PI CLI 后端、已经派发的 spec/job/session、Plus 用户手工重命名和原有项目路径均不受影响。名称创建与会话插入在 Plus Host 同一数据库事务完成，失败不留下只改一半的可见会话；不得为更名调用全局 `pi_project_open` 或把 `projectPath` 改成原仓库路径。

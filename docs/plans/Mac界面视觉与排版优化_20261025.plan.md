# Mac 界面视觉与排版优化

## 概要

对象：macOS「Kaneo 调度台」的总览、任务列表、任务详情浮层、侧栏与工具栏、命名，以及执行页的复盘，外加「设置」的四个页面（连接、项目、规划与评审、高级；S10）。要解决四类问题：信息太密、重点不突出；颜色与对比度不足；入口拥挤、叫法不统一；观感不像原生 Mac。

安卓控制台的同类优化是姊妹计划 [Android界面视觉与排版优化_20261025.plan.md](Android界面视觉与排版优化_20261025.plan.md)。两份计划共用状态词、泳道色、时长写法三套规则，规则以本文 S0、S8 为准；`docs/mobile-console-contract.md` 由安卓计划的 A0 修改，两边的规格改动须一并合入（风险 9）。

对照材料：设计画布（私有，仅作者可打开）https://claude.ai/artifact/DeJQQDPpkKegs3EspV2A1f ，当前为 Version 13，共 23 块画板：Mac 13 块（封面、问题清单、令牌 2 块、外壳、总览 3 块、任务列表 2 块、任务详情 2 块、执行复盘）、安卓 5 块、设置页 4 块，另有 1 块「现状问题清单 · 安卓与设置页」。「当前」画板由代码还原，不是真实截图；设置页的「当前」画板是按代码重画的 grouped Form 草图，系统表单的行高、标签位置、分区间距都是近似；「优化后」是示意稿，高度、宽度为估算（约 ±15%）。画板与本文有出入时以本文为准（连接页、高级页画板上残留的「待确认」字样，在画板发布后已得到确认，见「用户已确认」第 11、12 项；项目页画板的「当前」说明把整页高度约 1590pt 写成了详情高度，详情本身约 1476pt；外壳与任务列表的「优化后」画板把「看板 | 列表」画在工具栏最左、「规划待办…」排在筛选菜单之后，本文取控件顺序不变——与规格 §4.13 `:351` 和 `BoardView.swift:187-238` 的现行顺序一致，只改筛选菜单标题并把「更多」换成图标）。

状态：第二轮实施中（2026-10-26）。第一轮 KP-UI01（`ea0749c`、`2cbd781`）已由 `793fed8` 撤回，撤回记录见 `feat/20261026-kp-ui01-mac-visual-layout` 分支。本轮由 Claude 在 `claude/mac-ui-visual-typography-4180cf` 按本计划重做，已提交 `c92b661` 并推送；云端 `Packages` 首次运行失败于 3 处 Swift 编译错误，已修复；修复后的 `7612627` 与分片改动后的 `41c6444` 两次运行全部成功（含 macOS 编译与 Universal DMG 构建），未在本机编译；进度与未完成项见文末「实施记录」。计划基线为 `8aa7378`（初版 `63169b7`，修订与安卓姊妹计划同在 `8aa7378`）。

## 风险

1. `DetailSection` 标题降为 15pt 是全局变化，会波及 PendingView 请求详情（6 处）、会话阅读器状态卡（2 处）和 TaskDetailTabs（10 处）。
2. 设置页之外 230 行 `.secondary` 的机械替换（S1）和设置页 128 行的人工替换（S10）都可能误伤需要系统语义的地方（禁用态、占位）；替换后必须抽查 diff。
3. 状态徽标的样式一旦仍按标签文字反查，核心新增标签会显示灰色问号。S2 第 3 条用 `severity` 和 `kind` 决定样式，夹具覆盖。
4. 命名色是手写 `Contents.json`，本机无法编译核对，只能由云端构建验证。
5. ⌘R 在侧栏收起时可能失效，见 S3 第 3 条。
6. 900pt 工具栏是否溢出、搜索框是否自动收起，画布是估算（宽度约 ±15%），需实机核对。
7. 概览新顺序改变 VoiceOver 与键盘焦点顺序，必须按新顺序核对。
8. 列表行的开放提问判断改读 `TaskSummary` 新增的 `execution_question` 小结构（`state`、`answerable`）：核心的行里带这个字段是现状（`derive.py:594`），Swift 一侧是新增解码，夹具要补带它的 `TaskSummary` JSON（S9）。读不到时列表行回落为「需人工处理」，不会出错，但会失去区分。
9. 与 Android 共用的规则：状态词（契约 `mobile-console-contract.md:137` 现规定非失败类异常一律显示「阻塞」，要改为取核心标签）、泳道色（两端按角色上色）、时长写法、列表行前缀，由本文 S0 与安卓计划 A0 一并规定。两份计划的规格改动须一并合入；Mac 与安卓的实现分属不同计划和各自的云端构建，任何一端先上线，都会出现两端措辞或颜色不同的窗口期。
10. 估算数字：优化前后纵向高度、首屏占比、工具栏控件宽度，以及设置页四页的高度与首屏位置，都是按代码推算或在浏览器里量取，不是实测。
11. 设置页画板是按代码重画的 grouped Form 草图，没有真实的系统表单渲染（Form 内 `TextField` 的标签位置、行高、分区间距都是近似）。
12. 首屏余量小于估算误差：连接页执行环境整组约 535pt、保存约 496pt（首屏约 548pt）；项目页自动处理卡的保存约 680–704pt（首屏约 708pt）；规划与评审页 Review 环境整组约 527pt（首屏约 548pt）。「在首屏内」不是结论，要在实机上核对。
13. 默认折叠可能把异常藏起来：诊断、接收详情、PI CLI 环境检查、逐阶段开关都按「有异常则初始展开且标题带数量」处理；这些是 SwiftUI 视图状态，Swift 夹具不覆盖，只能人工核对。
14. 删除执行环境里的「连接 Plus」后，执行环境内不再有探测未保存草稿路径的入口，改在「本机 MCP 服务」里填路径探测。两个连接文件路径输入框仍并存，只改名区分（一个随执行配置保存，一个仅供探测、不保存）。
15. 定时检查编辑器折叠：草稿由父视图持有，折叠不丢未保存的改动；展开时的 `onAppear` 只在来源（`automationId`、`rrule`）变化时重新播种。「改一半 → 折叠 → 刷新 Desktop 状态 → 展开」要在实机上走一遍。
16. 项目页宽度阈值不变：低于 720pt 时上下堆叠（列表最高 220pt，详情在首屏里只剩约 220pt，估算）；900×600 最小窗口按侧栏占宽估算可能落在堆叠分支，三张卡在窄屏下的可读性要实机核对。
17. 菜单栏「刷新引擎状态」（`MenuBarView.swift:40`）与设置页新的「检查状态」叫法不同（菜单栏不在本轮）。
18. 引擎卡内保留 3 个保存按钮：`set-project-engine-mode`、`set-project-verify-env`、`set-project-fallback-model` 各自带 `expected_revision`，合并成一个保存需要处理部分成功，本轮不做。
19. 设置页没有 Swift 夹具覆盖（`macos/tests`、`tests` 里没有对这三个文件的引用），S10 的云端结果只能证明能编译。
